# Agent-Hub – selbst gehostetes Verwaltungstool (Raspberry Pi)

Projekte als Kacheln, Kanban-Board, feste KI-Agenten-Rollen, Dateiablage, Tresor für Zugangsdaten.
Ziel, Entscheidungen, Reihenfolge, Codeaufbau, Betrieb, Tests und offene Punkte: PROJEKT.md (dort zuerst nachlesen, Abschnitt „Auf einen Blick“ und Abschnitt 12 „Änderungsprotokoll“). Gestaltung: DESIGN.md. Übergabe des letzten Arbeitstags: CHAT-ZUSAMMENFASSUNG.md. Stand und nächste Schritte der Dateiablage: PROJEKT.md Abschnitt 11b.

## Zusammenarbeit
- Janis bestimmt die Struktur. Vor dem Code: erst die Schnittstelle zeigen (Signaturen, Datenformat), dann die Implementierung.
- Kleinste Lösung, die die Anforderung erfüllt. Keine Abstraktion auf Vorrat. Standardbibliothek zuerst; jede neue Abhängigkeit nennen und begründen.
- Ein Modul pro Auftrag. Jede Entscheidung kurz erklären, inklusive verworfener Alternative.
- Janis will den Code verstehen, aber keine Verständnisfragen am Ende einer Antwort (gestrichen am 07.11.2026). Entscheidungen weiter kurz erklären.
- Zugangsdaten, Schlüssel und Tokens nie ausgeben, nie ins Git, nie raten. Sie liegen im Tresor oder in der `.env`.
- Destruktive oder systemweite Befehle (Löschen, Docker-Volumes entfernen, `sudo`, Änderungen am Netzwerk) vorher von Janis bestätigen lassen. Keine Ports für Vorschauen freigeben.
- Routine (Commit, Merge, Push fertiger Änderungen) ohne Rückfrage, danach kurz berichten. Nachfragen nur bei Berechtigungen, Sicherheit sowie Design- und Feature-Entscheidungen.
- Hardware am Fahrzeug (Roadster, Heizung, Relais, Bordnetz) nie autonom schalten oder testen; das macht Janis vor Ort.
- **Tests dürfen nie an die echten Daten:** Der Testbefehl hängt immer ein leeres `/data` ein (`-v "$(mktemp -d):/data"`, PROJEKT.md Abschnitt 9). Am 13.11.2026 haben Testläufe echte hochgeladene Dateien gelöscht.
- **Diagnosebefehle geben nie Geheimnisse aus:** `docker inspect`, `env`, `ps`, `docker logs` und Ähnliches können Tokens enthalten (am 13.11.2026 stand der Tunnel-Token in einer Ausgabe). Nur die nötigen Felder ausgeben oder die Ausgabe filtern.
- Neue Pflichten, Entscheidungen und Änderungen gehören am Ende eines Auftrags in PROJEKT.md (Stand, Änderungsprotokoll) und bei Gestaltung in DESIGN.md.

## Architektur (Stand, Details in PROJEKT.md)
- Raspberry Pi 4B, Raspberry Pi OS Lite 64-Bit, alles per Docker Compose unter `/opt/agent-hub/`.
- Python mit FastAPI, SQLite, schlichtes Frontend (serverseitige Vorlagen, kein Framework). Läuft live unter `hub.janis-home.de`.
- Zugriff von außen nur über Cloudflare Tunnel (seit 13.11.2026 mit `--protocol http2`, QUIC war per WLAN zu langsam), keine offenen Router-Ports. Login mit E-Mail und Passwort, Rollen Owner (genau einer, übertragbar), Admin, Nutzer; Einladung und Passwort-Reset per E-Mail über Resend.
- Claude Code läuft über den Runner auf dem Pi, ein Wegwerf-Container je Lauf. Live: Claude und Mistral verknüpfen pro Nutzer, der Manager-Chat und seit 15.11.2026 die Agentenläufe (Board-Karte → Programmierer → Tester → Prüfer → Freigabe → Manager dokumentiert). Jede KI hängt hinter einem Adapter (`runner/adapters.py`: Claude Code, Mistral Vibe); der Nutzer hat eine **Standard-KI** mit Rückfall auf seine nächste KI (`aichoice.py`). Für Swift später ein Mac-Programm (nur ausgehend, Start per Knopf ohne zweite Anmeldung, Ergebnis als Git-Bundle über den Hub).
- Netz der Agenten: internes Docker-Netz, einziger Ausgang der Filter-Proxy `egress` (3129 nur Anthropic, 3128 öffentliche Seiten); nie ins Heimnetz. Geräte nur über Geräteliste und Vermittler, fremde Netze über Tailscale; auf der Fritzbox wird kein Port geöffnet.
- Jeder Nutzer verbindet sein eigenes Claude-Konto; die Konten sind strikt getrennt (Pflichtregeln in PROJEKT.md Abschnitt 3, „Trennung der Claude-Konten“).
- Pro Aufgabe ein Git-Branch (Worktree). Ablauf: Programmierer, Tester, Prüfer, Freigabe durch Janis, danach führt der Manager die Doku nach (Rolle Dokumentator entfallen am 07.11.2026).
- **KI-unabhängig (Konzept festgelegt 14.11.2026, KONZEPT-AGENTEN.md Abschnitt 9):** Der Hub ist das Gehirn, jede KI nur Rechenleistung hinter einem Anbieter-Adapter. Alles Neue, das eine KI anspricht, baut auf dem Paket (Regeln, Erinnerung, Lage, Auftrag) und dem festen Antwortformat auf (`<memory file>`, `<read>`, `<ask>`, `<task>`, `<status>`, `RESULT:`); nichts darf an Eigenheiten eines Anbieters hängen.
- Agenten nutzen Zugangsdaten nur über den Vermittler, nie direkt. Das gilt auch für Claude selbst: Läufe bekommen nie den Claude-Token, nur ein Ticket; der Gateway im Egress-Proxy setzt den Token ein (`runner/tokens.py`, PROJEKT.md Abschnitt 3). Neue Läufe bauen auf einem Adapter in `runner/adapters.py` auf (Ticket statt Zugangsdaten, Gateway je KI im Egress-Proxy: Claude 3130, Mistral 3131), nie mit eingehängtem Login-Ordner. Ein Lauf sieht nur seinen Arbeitsordner ohne `.git`; Git macht der Runner von außen (`runner/workspace.py`).

## Coding-Regeln
- Code, Klassen, Variablen, Dateinamen und Kommentare auf Englisch. Oberfläche und Doku auf Deutsch.
- Bewegung in der Oberfläche folgt dem Skill `apple-design`: Federn aus `web/app/static/motion.js` (Ziehen: `sortable.js`) statt fester Dauern, immer unterbrechbar, nur `transform` und `opacity`, `prefers-reduced-motion` beachten. Neue Zieh-Listen nutzen `Motion.sortable`. Details in DESIGN.md Abschnitt 6.
- Die Oberfläche ist zweisprachig (Deutsch und Englisch, pro Nutzer wählbar). Jeder neue Text, auch in Mails, kommt in `web/app/i18n.py` in beide Sprachen, nie fest im HTML oder JavaScript. Neue Seiten bauen auf `ui.logged_in_page()` / `layout.page()` auf, neue Routen kommen als Router in `web/app/routes/`.
- **Texte kurz und allgemein (Janis, 11.11.2026):** Oberflächentexte nennen weder „Pi“ noch „Stick“ noch Einzelheiten von Hardware oder Technik, sondern „Server“, „Festplatte“, „Daten“; keine Bedienhinweise, die nur für ein Gerät stimmen (z. B. wie man den Server wieder einschaltet), und keine Aufzählungen dessen, was intern passiert. Ein bis zwei kurze Sätze, nur was der Nutzer braucht.
- Für Oberfläche und Swift/iOS-Teile gelten die Apple Human Interface Guidelines (Bedienung, Layout, Typografie, Farben, Barrierefreiheit) und die Apple-Richtlinien für Swift und die App Review. Bei Zielkonflikten mit dem Projektsheet fragt Claude nach. Das konkrete Design (Farben, Glas, Knöpfe, Hell/Dunkel, Mails) steht in DESIGN.md und ist für jede Oberfläche verbindlich.
- **Mandantentrennung:** Jede Datenfunktion bekommt die `user_id` und prüft den Besitz (Projekt, Punkt, Konto); Fremdes ist „nicht gefunden“ (404) oder „nichts getan“. Das gilt auch für Code, den Agenten aufrufen. Neue Funktionen bekommen einen Fall in `web/tests/test_isolation.py`.
- **Rechte prüft der Server**, nicht das Menü (`users.can_manage`, Rollenprüfung in der Route). Ernste Aktionen (Löschen, Zurücksetzen, Owner übergeben) verlangen das Passwort des Handelnden (`deps.reauth`, mit Sperre pro IP). Offene Routen, die Mails auslösen oder Passwörter prüfen, bekommen eine Begrenzung (`throttle.py`).
- **Tokens** (Sitzung, Reset-Link) stehen in der Datenbank nur als Hash. Links in Mails kommen aus `HUB_BASE_URL`, nie aus der Anfrage. Mails nur über `mail.py` und `mailtext.py`.
- **Datenbank:** Schemaänderungen über `db.py`; Umwandlungen alter Daten laufen einmalig, nie bei jedem Start; eine Migration wird vor dem Deploy an einer Kopie der echten Datenbank geprobt; vor jedem Deploy ein Backup.
- **Text an Claude** (Projektkontext, Berichte, Fragen) geht nur über die Standardeingabe und ist als Information markiert, nie über die Befehlszeile; der Kontext kommt nur aus Daten des Besitzers. Der Launcher nimmt nur geprüfte Werte (Zahlen, Modell und Stufe nach festem Muster, Modus aus `CHAT_MODES`); ob Modell und Stufe in der Liste stehen, prüft der Hub (`catalog.check`).
- **Eine neue KI (Janis, 15.11.2026):** bekommt einen Adapter in `runner/adapters.py`, einen Eintrag in `catalog.py` (Modelle, Stufen, eindeutige Kennungen), eine Verbindung (`claude_link.py` oder `ai_link.py`), einen eigenen Gateway-Port im Egress-Proxy und Texte ohne Anbieternamen im Code (Name aus `catalog.provider().name`). Das Gateway beantwortet eigene Fehler (unbekanntes Ticket) nie so, dass das Programm der KI sie für einen falschen Schlüssel hält. Wer nur eine KI hat, muss alles nutzen können.
- **Agentenläufe:** Ein Lauf sieht nur seinen Arbeitsordner ohne `.git`; Git macht der Runner mit abgeschalteten Hooks (`runner/workspace.py`). Zusammengeführt wird erst nach der Freigabe des Nutzers, dann dokumentiert der Manager. Wie viele KI-Läufe gleichzeitig laufen, bestimmt die Einstellung des Owners (`serversettings.ai_parallel`), nie eine feste Zahl im Code.
- **Erinnerung:** Feste Dateien je Projekt (MEMORY, PROJEKT/PROJECT, ROADMAP, REGELN/RULES, ARCHIVE); `ARCHIVE.md` wächst nur (der Hub hängt mit Datum an), dort steht, was verworfen oder geändert wurde und warum. Neue Dateien im Grundgerüst bekommen eine Version (`memory.SINCE`), ältere Projekte erhalten sie einmalig.
- **KI-Modelle nie fest im Code (Janis, 14.11.2026):** Modelle und Stufen kommen aus `catalog.py` (Liste je Anbieter in `server_settings`), gewählt wird mit dem Baustein `ui.model_picker` (zwei Drop-downs: Modell und Stufe). Neue Stellen mit Modellauswahl nutzen genau diesen Baustein.
- **Keine Browser-eigenen Ausgaben (Janis, 13.11.2026):** nie `title` per Skript setzen (der Browser zeigt dann seinen grauen Kasten; `core.js` übernimmt `title` nur beim ersten Darüberfahren): für Hinweise `data-tip` setzen; kein `alert`, `confirm` oder `prompt`; keine Browser-Auswahllisten und -Prüfblasen (siehe DESIGN.md Abschnitt 9). Meldungen gehören in die Oberfläche selbst, an einen festen Platz, **nicht** als Fläche, die über Inhalt schwebt.
- **So wenig Neuladen wie möglich (Janis, 14.11.2026):** Änderungen tauschen nur ihren Teil der Seite (`AgentHub.swap`), Dialog-Formulare senden per `fetch`; was ein Neuladen zerstören würde (Hochladen), hält es mit `AgentHub.hold` an. Volles Neuladen nur als Rückfall (DESIGN.md Abschnitt 4).
- **Dialoge:** `display: flex` oder `grid` nur für `dialog[open]`, nie für den geschlossenen Dialog (ein geschlossener Dialog muss `display: none` bleiben; sonst steht er immer da und lässt sich nicht schließen).
- **Oberfläche:** Auswahlfelder immer im eigenen Stil (`.has-select`, Liste aus `core.js`), nie die Liste des Browsers, und ohne `title` (der Hinweis deckt sonst die Liste zu).
- **Skins mitdenken (Janis, 15.11.2026):** Das Aussehen soll später als Skin austauschbar sein (Anordnung bleibt). Farben, Formen, Glas und Schatten daher nur über Design-Variablen (`:root`) und gemeinsame Klassen, nie fest in ein einzelnes Bauteil. Mitgeliefert bleiben nur Hell und Dunkel.
- **Design der Projekte:** steht in `REGELN.md`/`RULES.md` des Projekts unter „Design“, keine eigene Datei (auch bei einem Import).
- **Bausteine statt Einzelstücke (Janis, 14.11.2026):** Erklärungen als „i“ neben Überschrift oder Knopf (`ui.info_dot`), nie als Unterzeile; Wechsel zwischen Ansichten mit dem Segmentschalter (`static/segment.js`, quer oder hochkant, ziehbar); Höhe zweier Kacheln über den Trenner (`.m-split`, `static/splitter.js`); kleine runde Knöpfe im gemeinsamen Glas-Design (DESIGN.md Abschnitt 4). Kein neues Knopfdesign ohne Rückfrage. Erklärungen zu schwierigen Einstellungen über ein „i“ (`.info-dot` mit `data-tip`, DESIGN.md Abschnitt 4), nie als fester Textblock. Klassen in einer Ansicht mit Präfix, wenn ein Name schon vergeben ist (Manager: `m-`).
- **Klare Designsprache, Bereiche getrennt (Janis, 11.11.2026):** Jeder Bereich zeigt nur seine eigenen Bedienelemente, nichts wird vermischt. Board-Tab = alle Punkte in jedem Zustand (offen, Vorschlag, Papierkorb, Archiv) samt deren Knöpfen; Manager-Tab = nur Managen (Chat, Status, Prüfungen, Geräte, Dateien). Ein neues Bedienelement gehört in genau einen Bereich; ist unklar, in welchen, fragt Claude nach (DESIGN.md, Abschnitt 1).
- **Board und Manager:** Das Board ist nur für Software (Bugs, kleine und Major-Updates). Hardware-To-Dos, Checklisten und regelmäßige Prüfungen gehören dem Manager. Einstellungen gelten pro Nutzer und pro Agent: Modell und Schalter „Web + Code zusammen“ hat jede Rolle selbst (`agents.configure(user, rolle, ...)`, der Manager ist `chef`); die Selbstständigkeit gehört dem Manager.
- **Kein Skript im HTML (15.11.2026):** Skripte nur als Datei aus `/static`, nie im HTML und nie als `on…`-Attribut; die Content-Security-Policy (`CONTENT_POLICY` in `web/app/main.py`) lässt nichts anderes laufen. Jede neue fremde Quelle (Bilder, Schriften, Verbindungen) wird dort bewusst eingetragen und begründet.
- **Weiterreichen mit Geheimnis (15.11.2026):** Code, der eine Anfrage mit eingesetztem Token oder Schlüssel weiterleitet (Gateway im Egress-Proxy), lehnt Steuerzeichen (CR, LF, NUL) in Zeilen ab, baut den Kopf selbst neu auf und reicht genau eine Anfrage je Verbindung weiter. Jeder Schmuggelfall bekommt einen Test.
- **Hintergrundarbeit meldet immer ihr Ende (15.11.2026):** Jeder Auftrag des Runners (Chat, Lauf, Schlüssel, Merge) endet mit einer Meldung an den Hub, auch bei unbekannten Werten oder Fehlern; nichts bleibt hängen, bis ein Zeitlimit greift. Unbekanntes vom Hub ist ein sauberer Fehlschlag, nie ein Abbruch.
- **Löschweg mitbauen (15.11.2026):** Was außerhalb der Datenbank entsteht (Dateien, Repos, Arbeitsordner, Schlüssel), bekommt beim Bau einen Löschweg für „Projekt gelöscht“ und „Konto gelöscht“, mit Test. Nichts von einem gelöschten Nutzer bleibt liegen. Ein gelöschtes Konto ist 30 Tage nur gesperrt (`users.deleted_at`, Wiederherstellen durch erneutes Einladen), danach bleibt nichts, auch kein Vermerk (`users.purge_deleted`). Abfragen nach Konten sehen nur aktive. Tabellen, deren Nummer ein Ordner auf der Platte trägt (Konten, Projekte, Aufgaben), vergeben neue Nummern mit `db.fresh_id`, nie eine, deren Ordner noch auf das Löschen wartet.
- **Übergangscode mit Datum (15.11.2026):** Ein Rückfall für alte Daten oder alte Formate trägt im Kommentar das Datum und wird entfernt, sobald es die alten Daten nicht mehr geben kann. Code, den nur noch Tests benutzen, wird samt dieser Tests gelöscht. Was doppelt steht, wird eine Funktion.
- **Feste Versionen in Images (15.11.2026):** Jedes Programm in einem Image hat eine feste Version (wie `mistral-vibe` in `runner/Dockerfile.vibe`); eine neue Version wird zuerst auf einem Branch probiert.
- **Eingabefelder am Handy (15.11.2026):** Auf Geräten mit Fingerbedienung haben Eingabefelder mindestens 16 px Schrift, sonst zoomt der Browser beim Tippen hinein.
- **Mails (16.11.2026):** Vor jeder Änderung an Mails `MAILS.md` lesen. Keine Bilder, alles Nötige inline, Hell als Grundlage und Dunkel über `prefers-color-scheme`, Farben, die fremdes Umfärben überstehen, Zugaben nur per CSS mit fester Farbe darunter; neue Erkenntnisse aus echten Mailprogrammen kommen dort hinein.
- **Mail-Einrichtung (15.11.2026):** SPF, DKIM und DMARC der Absender-Domain gehören zur Einrichtung einer Instanz und in die Checkliste vor dem Livegang (PROJEKT.md Abschnitt 11).
- Nur ein Thema pro Commit, kurze englische Commit-Nachrichten, ein Branch pro Aufgabe.
- Backups und Rückrollen sind Teil jeder Änderung, die Daten betrifft.

## Arbeitsablauf
1. Janis skizziert Modul und Schnittstelle, Claude prüft auf Schlankheit.
2. Kleine Schritte, ein Modul pro Auftrag, jeweils mit Erklärung.
3. Entwickeln und Testen: Am Windows-PC ohne Git über den Klon auf dem Pi (Ablauf in PROJEKT.md Abschnitt 9, „Arbeitsablauf vom PC aus“), später auch am Mac. Git von Anfang an, ein Branch pro Aufgabe. Vom PC aus kein verschachteltes Anführungszeichen-Gemisch für `ssh`: Skript schreiben, mit `scp` hochladen, mit `bash` ausführen.
4. Tests im Container (Unit-Tests, HTTP-Test mit zwei Konten), dann Merge nach `main`, Push, Backup, Deploy per `docker compose up -d --build web`, Prüfung von `/health` und der Live-Seite.
