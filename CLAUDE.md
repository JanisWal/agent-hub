# Agent-Hub – selbst gehostetes Verwaltungstool (Raspberry Pi)

Projekte als Kacheln, Kanban-Board, feste KI-Agenten-Rollen, Dateiablage, Tresor für Zugangsdaten.
Ziel, Entscheidungen, Reihenfolge, Codeaufbau, Betrieb, Tests und offene Punkte: PROJEKT.md (zuerst „Auf einen Blick“ und der Fahrplan in 11a). Verlauf aller Änderungen: PROTOKOLL.md. Gestaltung: DESIGN.md. Agenten und KI-Pakete: KONZEPT-AGENTEN.md. Mails: MAILS.md. Übergabe des letzten Arbeitstags: CHAT-ZUSAMMENFASSUNG.md.

## Zusammenarbeit
- Janis bestimmt die Struktur. Vor dem Code erst die Schnittstelle zeigen (Signaturen, Datenformat), dann die Implementierung.
- Kleinste Lösung, die die Anforderung erfüllt; keine Abstraktion auf Vorrat; Standardbibliothek zuerst, jede neue Abhängigkeit nennen und begründen.
- Ein Modul pro Auftrag. Jede Entscheidung kurz erklären, mit verworfener Alternative. Keine Verständnisfragen am Ende einer Antwort (07.11.2026).
- Zugangsdaten, Schlüssel und Tokens nie ausgeben, nie ins Git, nie raten; sie liegen im Tresor oder in der `.env`.
- Destruktive oder systemweite Befehle (Löschen, Docker-Volumes, `sudo`, Netzwerk) vorher von Janis bestätigen lassen. Keine Ports für Vorschauen freigeben.
- Routine (Commit, Merge, Push, Deploy fertiger Änderungen) ohne Rückfrage, danach kurz berichten. Nachfragen nur bei Berechtigungen, Sicherheit, Design und Features.
- Hardware am Fahrzeug (Roadster, Heizung, Relais, Bordnetz) nie autonom schalten oder testen; das macht Janis vor Ort.
- **Tests nie an die echten Daten:** immer mit leerem `/data` (`-v "$(mktemp -d):/data"`, PROJEKT.md Abschnitt 9; am 13.11.2026 haben Testläufe echte Dateien gelöscht).
- **Diagnosebefehle geben nie Geheimnisse aus:** `docker inspect`, `env`, `ps`, `docker logs` nur gefiltert (am 13.11.2026 stand der Tunnel-Token in einer Ausgabe).
- Am Ende eines Auftrags: Stand in PROJEKT.md, Eintrag oben in PROTOKOLL.md, Gestaltung in DESIGN.md; die Doku-Dateien in den iCloud-Projektordner kopieren.

## Architektur (Kurzfassung, Details in PROJEKT.md)
- Raspberry Pi 4B (1 GB), Raspberry Pi OS Lite 64-Bit, Docker Compose unter `/opt/agent-hub/`; Python mit FastAPI, SQLite, serverseitige Vorlagen ohne Framework; live unter `hub.janis-home.de`.
- Von außen nur über Cloudflare Tunnel (`--protocol http2`), keine offenen Router-Ports. Login mit E-Mail und Passwort, Rollen Owner (genau einer, übertragbar), Superadmin, Admin, Nutzer; Mails über Resend.
- Dienste: `web` (Hub), `runner` (Docker-Socket, startet je Chat-Frage und Agentenlauf einen Wegwerf-Container), `egress` (einziger Ausgang der Agenten: 3128 öffentliche Seiten, 3129 nur Anthropic, Gateways 3130 Claude, 3131 Mistral, 3132 eigene KI, 3133 ChatGPT), `broker` (Vermittler zu Geräten). Agentennetz intern, nie ins Heimnetz; fremde Netze über Tailscale, auf der Fritzbox kein offener Port.
- **Der Hub ist das Gehirn, jede KI nur Rechenleistung** (KONZEPT-AGENTEN.md 9): Jede KI hängt hinter einem Adapter (`runner/adapters.py`); was sie bekommt, baut `web/app/prompts.py`; sie antwortet im festen Format (`<memory-edit>`, `<memory file>`, `<task>`, `<task-edit>`, `<ask>`, `<device>`, `<read>`, `RESULT:`). Nichts hängt an Eigenheiten eines Anbieters. Jeder Nutzer hat eine Standard-KI mit Rückfall auf seine nächste eigene (`aichoice.py`); ist ihr Kontingent aufgebraucht, vertritt sie die nächste für die Ruhezeit auch in der Oberfläche (`aichoice.acting_in`, 22.11.2026).
- Jeder Nutzer verbindet sein eigenes KI-Konto; die Konten sind strikt getrennt (PROJEKT.md Abschnitt 3). Läufe bekommen nie Token oder Schlüssel, nur ein Ticket; das Gateway setzt die Zugangsdaten ein (`runner/tokens.py`).
- Pro Aufgabe ein Git-Branch. Kette (seit 22.11.2026, KONZEPT-AGENTEN.md 10): das Board ist die Warteschlange, der Programmierer nimmt einen Punkt (er verlässt das Board) → Tests des Projekts (`hub-test.sh`, führt der Hub aus; rot zurück) → Tester → Prüfer; jeder Mangel geht zurück zum Programmierer, danach läuft die ganze Kette wieder; ok des Prüfers → Merge durch den Runner → Manager dokumentiert. Keine Freigabe durch den Nutzer. Swift später über ein Mac-Programm (nur ausgehend, Ergebnis als Git-Bundle; Aufgaben mit `needs = mac`).

## Regeln für den Code

**Allgemein**
- Code, Bezeichner, Dateinamen und Kommentare auf Englisch; Oberfläche und Doku auf Deutsch. Ein Thema pro Commit, kurze englische Commit-Nachrichten, ein Branch pro Aufgabe.
- Kommentare sagen, was der Code tut und warum; die Geschichte gehört nach PROTOKOLL.md und ins ARCHIVE eines Projekts.
- **Übergangscode mit Datum (15.11.2026):** Rückfälle für alte Daten oder Formate tragen ihr Datum und gehen, sobald es die alten Daten nicht mehr geben kann (auch in keinem Backup, Backups halten bis 35 Tage). Code, den nur noch Tests benutzen, geht samt Tests. Was doppelt steht, wird eine Funktion.
- **Feste Versionen in Images (15.11.2026):** jedes Programm mit fester Version (Claude Code 2.1.319, `mistral-vibe` 3.1.2, Node 20.19 aus Debian); eine neue Version zuerst auf einem Branch.
- Backups und Rückrollen gehören zu jeder Änderung, die Daten betrifft.

**Oberfläche**
- Apple Human Interface Guidelines; das konkrete Design steht verbindlich in DESIGN.md. Bei Zielkonflikten nachfragen.
- Zweisprachig (Deutsch und Englisch, pro Nutzer): jeder Text, auch in Mails, in `web/app/i18n.py`, nie fest im HTML oder JavaScript. Neue Seiten auf `ui.logged_in_page()` / `layout.page()`, neue Routen als Router in `web/app/routes/`.
- **Texte kurz und allgemein (11.11.2026):** „Server“, „Festplatte“, „Daten“ statt „Pi“, „Stick“ oder Technik; keine gerätespezifischen Bedienhinweise, keine Aufzählung interner Abläufe; ein bis zwei Sätze.
- **Bereiche getrennt (11.11.2026):** Board-Tab = alle Punkte in jedem Zustand samt ihren Knöpfen; Manager-Tab = nur Managen (Chat, Status, Prüfungen, Geräte, Dateien). Ein neues Bedienelement gehört in genau einen Bereich; im Zweifel fragen (DESIGN.md 1).
- **Bausteine statt Einzelstücke (14.11.2026):** Erklärung als „i“ (`ui.info_dot`, `data-tip`), nie als Unterzeile oder Textblock; Segmentschalter `static/segment.js`; Trenner `.m-split` (rasten an einem feinen Raster ein: jede Zeile, Magnet 6 px, beim Loslassen 12 px, nach jedem Neuladen an derselben Stelle wieder; 22.11.2026); runde Knöpfe im gemeinsamen Glas-Design. Kein neues Knopfdesign ohne Rückfrage. Klassen mit Präfix, wenn ein Name vergeben ist (Manager: `m-`).
- **„i“ sparsam (18.11.2026):** nur bei Programmspezifischem (Hochladen, KI-Läufe, Ampel, Geräte, Manager-Chat, Backup), nie bei Allgemeinem und nie an ausgegrauten Platzhaltern; lieber ein klarerer Knopftext.
- **Bewegung** nach dem Skill `apple-design`: Federn aus `static/motion.js`, Ziehen mit `Motion.sortable`, unterbrechbar, nur `transform` und `opacity`, `prefers-reduced-motion` beachten (DESIGN.md 6).
- **Keine Browser-eigenen Ausgaben (13.11.2026):** kein `title` per Skript (Hinweise mit `data-tip`), kein `alert`/`confirm`/`prompt`, keine Browser-Auswahllisten und -Prüfblasen; Auswahlfelder immer `.has-select` ohne `title`. Meldungen an einem festen Platz in der Oberfläche, nie schwebend.
- **So wenig Neuladen wie möglich (14.11.2026):** Teile tauschen mit `AgentHub.swap`, Dialoge senden per `fetch`, laufende Uploads halten mit `AgentHub.hold` (DESIGN.md 4). **Ein Weg für alles (22.11.2026):** Aktionen, die etwas entfernen, mit `AgentHub.act(url, daten, {gone, parts})` (die Zeile faltet sich sofort weg); was dem Server von selbst folgt, nur über `AgentHub.live({parts | run, every, when})`, nie ein eigenes `setInterval` oder einen eigenen Seitenabruf.
- Dialoge: `display: flex`/`grid` nur für `dialog[open]`. **Nichts, was sich unter dem Zeiger bewegt, darf den Zeiger verlieren (22.11.2026, nach dem dritten Mal):** Knöpfe und kleine Bedienelemente heben sich nie (nur heller, beim Drücken nachgeben); Karten, die sich heben, behalten ihre Trefferfläche per Pseudo-Element 4 bis 5 px über jede Kante, hinter dem Inhalt (Muster `.file-row`); der Test `HoverTest` in `tests/test_loop.py` prüft jede Hover-Regel mit Verschiebung. Eingabefelder auf Fingergeräten mit mindestens 16 px Schrift.
- **Skins mitdenken (15.11.2026):** Farben, Formen, Glas und Schatten nur über `:root`-Variablen und gemeinsame Klassen; mitgeliefert nur Hell und Dunkel.
- **Kopieren und Markieren (21.11.2026):** Codes, Tokens, Schlüssel zum Einfügen und Befehle kopiert ein Klick (`ui.copy_button` in einer `.copy-box`, kurze Codes auch per Klick auf den Text, `.copy-click`; Skripte klonen `#copy-tpl`). Bedientext ist nicht markierbar (Knöpfe, Beschriftungen, Zustände, Reiter, Menüs, Überschriften der Oberfläche, Karten zum Klicken oder Ziehen), Inhalt schon (Chat, Beschreibungen, Datei- und Erinnerungstext, Adressen, Fehlermeldungen, Eingabefelder); die Liste steht in `app.css`.
- **Kein Skript im HTML (15.11.2026):** Skripte nur als Datei aus `/static`, nie inline oder als `on…`-Attribut (`CONTENT_POLICY` in `web/app/main.py`); jede neue fremde Quelle dort eintragen und begründen.
- **Mails (16.11.2026):** vorher MAILS.md lesen; keine Bilder, alles inline, Hell als Grundlage, Dunkel über `prefers-color-scheme`; Mails nur über `mail.py`/`mailtext.py`, Links aus `HUB_BASE_URL`. SPF, DKIM und DMARC gehören zur Einrichtung (PROJEKT.md 11).

**Sicherheit und Daten**
- **Mandantentrennung:** jede Datenfunktion bekommt die `user_id` und prüft den Besitz; Fremdes ist 404 oder „nichts getan“, auch für Code, den Agenten aufrufen. Neue Funktionen bekommen einen Fall in `web/tests/test_isolation.py`.
- **Rechte prüft der Server** (`users.can_manage`, Rollenprüfung in der Route). Ernste Aktionen verlangen das Passwort (`deps.reauth`, Sperre pro IP); offene Routen, die Mails auslösen oder Passwörter prüfen, bekommen `throttle.py`.
- Tokens (Sitzung, Reset-Link) nur als Hash in der Datenbank.
- **Datenbank:** Schemaänderungen über `db.py`; Umwandlungen alter Daten einmalig, nie bei jedem Start; jede Migration vor dem Deploy an einer Kopie der echten Datenbank proben; vor jedem Deploy ein Backup (mit der Backup-Funktion von SQLite, nie `cp`).
- **Löschweg mitbauen (15.11.2026):** Was außerhalb der Datenbank entsteht (Dateien, Repos, Arbeitsordner, Ansichten, Schlüssel), bekommt beim Bau einen Löschweg für „Projekt gelöscht“ und „Konto gelöscht“, mit Test. Ein gelöschtes Konto ist 30 Tage gesperrt (`users.deleted_at`), danach bleibt nichts (`users.purge_deleted`). Tabellen, deren Nummer einen Ordner trägt, vergeben Nummern mit `db.fresh_id`.
- **Zugangsdaten löschen nur bei Ablehnung (20.11.2026):** Ein Token oder Schlüssel wird gelöscht, wenn der Anbieter ihn klar ablehnt (401). Kann der Server ihn nicht lesen (`tokens.Unreadable`, z. B. falscher `HUB_TOKEN_KEY`), bleibt er und der Chat meldet einen Serverfehler.
- **Weiterreichen mit Geheimnis (15.11.2026):** Code, der eine Anfrage mit eingesetztem Token weiterleitet (Gateway), lehnt CR, LF und NUL ab, baut den Kopf neu, reicht genau eine Anfrage je Verbindung weiter und lässt nur die nötigen Pfade durch (`egress.path_allowed`). Jeder Schmuggelfall bekommt einen Test.
- **Hintergrundarbeit meldet immer ihr Ende (15.11.2026):** jeder Auftrag des Runners endet mit einer Meldung an den Hub, auch bei Fehlern (`Runner._guarded`, Meldungen werden wiederholt); Unbekanntes vom Hub ist ein sauberer Fehlschlag.

**KI und Agenten**
- **Pakete je Rolle (20.11.2026):** Texte an eine KI entstehen nur in `web/app/prompts.py`, gehen nur über die Standardeingabe, sind als Information markiert und kommen nur aus Daten des Besitzers. Jede Rolle bekommt nur ihre Regeln, ihre Markierungen (`prompts.ALLOWED`) und ihren Kontext: Manager im Chat MEMORY.md ganz, kleine Erinnerungsdateien, Projektlage; Programmierer RULES.md und die Aufgabe; Tester und Prüfer den Diff und das Testergebnis, der Prüfer dazu den Prüf-Schwerpunkt des Projekts; der Manager nach dem Merge MEMORY.md und ROADMAP.md, bei einer Rückfrage MEMORY, PROJECT und RULES. Bausteine, die nicht gebraucht werden (Geräte, Prüfungen), fehlen ganz.
- **Werkzeuge je KI (20.11.2026):** Im Katalog steht je Anbieter, welches Werkzeug die KI selbst hat (`own`), vom Hub bekommt (`hub`) oder nicht hat (`none`; `catalog.tools_of`). Das Paket nennt nur, was es gibt. Keine KI darf an einem fehlenden Werkzeug scheitern: fehlt es, bekommt sie das Werkzeug des Hubs (`runner/hub_tools.py`) oder den Inhalt im Paket (`<read>`). **Ersatz nur bei klarem Befund (21.11.2026):** Ein eigenes Werkzeug gilt erst als fehlend, wenn das Programm seine Werkzeugliste lesbar meldet und es darin dreimal hintereinander fehlt (`toolcheck.py`); unlesbare Listen und Fehler im Lauf zählen nie, sonst bleibt das eigene, sparsamere Werkzeug.
- **Eine neue KI (15.11.2026):** Hat sie nur eine API im OpenAI-Format, reicht die „Weitere KI“ (`custom`, bis zu acht Plätze `custom-1` … `custom-8` je Nutzer, `runner/hubloop.py`, Gateway 3132) ohne neuen Code; ein eigener Adapter nur, wenn ihr Programm eigene Werkzeuge und eine Abo-Anmeldung hat (Platzhalter `ui.SOON`). Sonst: Adapter in `runner/adapters.py`, Eintrag in `catalog.py` (Modelle, Stufen, eindeutige Kennungen, Werkzeuge, `images`), Verbindung (`claude_link.py` oder `ai_link.py`), eigener Gateway-Port, Texte ohne Anbieternamen im Code. Das Gateway beantwortet eigene Fehler nie so, dass die KI sie für einen falschen Schlüssel hält. Wer nur eine KI hat, muss alles nutzen können.
- **Grenzen eines kleinen Servers sind Einstellungen (21.11.2026):** Was nur wegen des Pi klein ist (Speicher, Prozessoren, Prozesse, Zeitlimits, Datenmengen je Lauf), steht in `serversettings.CHOICES` mit dem bisherigen Wert als Standard, wird in der Verwaltung gewählt und jedem Auftrag mitgegeben (`run_limits`); der Runner prüft die Werte selbst (`launcher.checked`). Feste Grenzen bleiben nur für Schutz und Token-Sparsamkeit.
- **Fehlerarten an einer Stelle (21.11.2026):** Warum eine KI scheiterte, entscheidet nur `failures.py` (Chat und Läufe); eine neue Meldung eines Programms bekommt eine Zeile dort und einen Fall in `tests/test_failures.py`.
- **Abo und API-Schlüssel (21.11.2026):** Ein Schlüssel neben dem Abo (Claude, ChatGPT) wird nur so genutzt, wie der Nutzer es einstellt (`credentials.py`: Modus, Bereich, Tagesgrenze); gewechselt wird nur vom Abo zum Schlüssel, nie zurück. Die Oberfläche nennt nie Preise, nur „Kann Zusatzkosten verursachen“. Am Gateway gilt das Ticket eines Abos nur in seiner Hülle, das eines Schlüssels nur bloß; beide nie zum Ziel des anderen.
- **Freigegebene Adressen (21.11.2026):** Weitere KIs nutzen das Netz des Servers (und http ohne s) nur an Adressen, die der Owner in der Verwaltung freigibt, je Adresse mit Port für alle Konten oder eines (`netaddresses.py`); nie der Server selbst oder das Docker-Netz. Adressen im Internet brauchen keine Freigabe. KIs in fremden Netzen später über VPN (PROJEKT.md 4).
- **Modelle nie fest im Code (14.11.2026):** aus `catalog.py`, gewählt mit `ui.model_picker`; der Hub prüft mit `catalog.check`. Seit 21.11.2026 kommen die Listen einmal am Tag von jeder KI selbst, je Nutzer (`models.py`); `catalog.SEED` ist nur der Start, jeder sieht nur die Modelle seines Kontos. Der Launcher nimmt nur geprüfte Werte (Zahlen, Modell und Stufe nach festem Muster, Modus aus `CHAT_MODES`).
- **Agentenläufe:** Ein Lauf sieht nur seinen Arbeitsordner ohne `.git` und, nur lesend, `/files` (der Manager-Chat zusätzlich `/code`; Ansichten je Inhalt zwischengespeichert, `runner/view.py`). Git macht der Runner mit abgeschalteten Hooks (`runner/workspace.py`). Die Tests des Projekts (`hub-test.sh`) laufen in einem eigenen Container ohne KI; grün geht zum Tester, rot zurück zum Programmierer. Vor jedem Lauf des Programmierers holt der Runner `main` in den Branch; Konflikte bleiben mit Markern für ihn in den Dateien. Ein Prüfer mit kleinem Diff und die kurzen Aufträge des Managers laufen ohne Werkzeuge. Zusammengeführt wird nach dem ok des Prüfers. Wie viele KI-Läufe gleichzeitig laufen, bestimmt `serversettings.ai_parallel`.
- **Läufe ohne festes Zeitlimit (22.11.2026):** Ein Lauf streamt seine Ausgabe; der Runner meldet ihn alle paar Sekunden (`/runner/runs/{id}/alive`, hält das Ticket gültig) und beendet ihn nur bei Stillstand oder nach der Höchstdauer (Einstellungen). Ein beendeter oder gescheiterter Lauf behält seinen Stand und läuft einmal weiter, beim zweiten Mal entscheidet der Nutzer. Beim Start sagt der Runner `hello`, der Hub stellt dessen Läufe und Chat-Antworten zurück in die Warteschlange.
- **Entscheidungen statt Eskalation (22.11.2026):** Eine Aufgabe, die nicht weiterkommt (zu viele Rückgaben, nichts geändert, zweimal gescheitert, kein gültiges Ergebnis), hält an (`agent_tasks.hold = decision`); der Manager erklärt in einfachen Worten und empfiehlt, der Nutzer wählt in „Wartet auf dich“ Weiter (mit Hinweis), So übernehmen oder Abbrechen. Fehlt nur die Zeile `RESULT:`, fragt der Hub dieselbe KI einmal nach. Sind alle KIs des Nutzers verbraucht, wartet der Lauf.
- **Fehlerlisten (21.11.2026):** Meldet der Nutzer mehrere Mängel auf einmal, wird jeder eigene Mangel ein eigener Fehler (gleiche Ursache, ein Fehler); keine Obergrenze je Antwort (nur eine Notbremse bei 60, `reply.MAX_TASKS`; der Runner reicht 100 000 Zeichen weiter), nichts geht verloren.
- **KI je Rolle (22.11.2026):** Jede Rolle kann ihre eigene KI haben (Pillen im Rollen-Tab, `agents.role_provider_in`); ohne Wahl gilt die Standard-KI. **Notschalter:** „KIs pausieren“ in der Schublade friert die Agentenläufe des Nutzers ein (`docker pause`, nichts wird beendet, die Zeit steht still) und startet nichts Neues, der Manager-Chat bleibt frei.
- **Was eine Rolle aufs Board legt (21.11.2026):** Alles, was zur Aufgabe gehört (Feinschliff, Randfälle, kleine Fehler im berührten Code), erledigt der Programmierer im Lauf; Tester und Prüfer melden es als Ergebnis. Aufs Board dürfen Rollen nur einen Fehler außerhalb der Aufgabe (sofort) und eine neue Funktion (wartet). Was nur der Nutzer in der echten Welt tun kann (Gerät anschließen, Konto anlegen, echte Daten), meldet eine Rolle mit `<env>`: ein Eintrag in „Für dich“; geht ohne nichts, endet sie mit `RESULT: blocked` und die Aufgabe wartet, bis er abgehakt ist. **Selbst weitermachen (22.11.2026, nachts):** fehlt eine Datei, legt die Rolle eine eigene Probe an oder macht ohne weiter; Aussehen prüft sie selbst im Test-Browser (`--shot`, Bild ansehen); beides ist nie `<env>` und nie eine Empfehlung an den Nutzer. Fragen einer Rolle (`<ask>`, `RESULT: question` hält an) gehen zuerst an den Manager: er entscheidet nach der Selbstständigkeit selbst oder schreibt sie einfach und mit Vorschlag für den Nutzer neu; Antworten gehen nie in den Manager-Chat. Doppelte erkennt `reply.similar` für Board und Fragen.
- **Vom Chat zum Programmierer (19.11.2026):** Der Manager zerlegt Wünsche in kurze Stichpunkte mit Kontext (`board_items.details`); was der Nutzer will oder von Hand anlegt, steht offen in der Warteschlange und startet ohne Bestätigung (`agents.take_next`, die einzige Stelle, die Aufgaben anlegt: je Projekt eine, Fehler zuerst, sonst in der Reihenfolge des Anlegens; wartet eine Aufgabe auf den Nutzer, wartet der Rest). Der Manager fragt Unklares direkt im Chat. Eigene Vorschläge des Managers und Funde einer Rolle warten auf das Ja (ein Bug nicht). Was der Nutzer will, startet auch dann sofort, wenn der Manager dafür im Web gelesen hat (22.11.2026, die Regel vom 20.11. ist aufgehoben). Ein Punkt ohne `from` gilt als Wunsch des Nutzers, nur `from="idea"` wartet (22.11.2026). Werte und Klassen nennen keine KI (`source`: `user`, `agent`, `manager`).
- **Board und Manager:** Das Board ist nur für Software. Hardware-To-Dos, Checklisten und regelmäßige Prüfungen gehören dem Manager. Einstellungen gelten pro Nutzer und Rolle (`agents.configure`, der Manager ist `chef`); Tester und Prüfer standardmäßig ohne Internet; die Selbstständigkeit gehört dem Manager.
- **Erinnerung:** feste Dateien je Projekt mit englischen Namen (MEMORY, PROJECT, ROADMAP, RULES, ARCHIVE); das Design eines Projekts steht in RULES.md unter „Design“, nie in einer eigenen Datei (auch bei einem Import). Die KI ändert per Abschnitt (`<memory-edit>` mit `<section title>`), ARCHIVE.md wächst nur (der Hub hängt mit Datum an). Neue Dateien im Grundgerüst bekommen eine Version (`memory.SINCE`).
- **Bilder und PDFs (18.11.2026):** jede KI muss sie selbst ansehen können (Werkzeug `look` als Ersatz, nur lesend, nur `/files`, `/code`, `/work`); ob ein Modell Bilder sieht, steht im Katalog (`images`). Nie Text aus fremden Dateien auf dem Server ziehen.
- **Gedanken der KI (18.11.2026):** nur zum Anzeigen (`thought(line)` im Adapter, `chat.add_thoughts`), nie im Kontext, nie im Archiv, nie Grundlage einer Aktion.
- **Verbrauch nur über das Verbrauchsbuch (22.11.2026):** Jeder Aufruf einer KI landet genau einmal in `ai_usage` (`usage.record`, geschrieben in `chat.finish` und `agents.finish_run`), mit KI, Modell, Abo oder Schlüssel, Eingabe gesamt, Ausgabe und dem Anteil aus dem Zwischenspeicher; auch beendete und abgebrochene Läufe (`partial`, aus dem Stream). Eine neue Art von KI-Auftrag oder ein neues Programm meldet seine Zahlen auf diesem Weg; Zahlen aus `agent_runs` oder `chat_messages` sind nie die Auswertung. Geschätzt wird nichts.
- **Kleine KI-Aufträge des Hubs** (Status, `statusnote.py`): knapper Auszug, günstigstes Modell (`catalog.light`), ohne Werkzeuge, nur bei Änderungen, nie im Chat. Sie brauchen keinen freien KI-Platz, gehen aber nie vor einer Frage des Nutzers (22.11.2026).

**Geräte**
- **Geheimnisse (17.11.2026):** nie auslesbar, nur ersetzen oder entfernen; entschlüsseln darf nur der Vermittler, der Web-Dienst nur verschlüsseln (`pyrage`). Schlüssel für die KI, Passwort für den Menschen; die KI sieht nie ein Geheimnis. Shell und Dateibrowser eines Geräts sind für den Menschen; die KI löst außerhalb des Programmierer-Kontexts nur feste, freigegebene Aktionen aus. Entschieden, noch nicht gebaut (18.11.2026): im Programmierer-Kontext Shell auf freigegebenen Geräten über den Vermittler per Ticket (PROJEKT.md 11a, Stufe 4).
- **Vermittler (17.11.2026):** jede Geräteverbindung geht durch `broker/broker.py`; Befehle nur aus `web/app/device_profiles.py`, nie Text von Nutzer oder KI auf einer Befehlszeile; der Vermittler prüft Ziele, Hostschlüssel und Herkunft selbst.
