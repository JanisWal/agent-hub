## 1. Ziel und Philosophie

- Ein selbst gehostetes Verwaltungstool für Software-Projekte auf einem Raspberry Pi: Projekte als Kacheln, Kanban-Board, feste KI-Agenten-Rollen, Dateiablage.
- Hobbyprojekt, aber in Bausteinen und offen gedacht: Freunde können das Grundgerüst auf einem eigenen Pi installieren.
- Janis baut es per Vibe-Coding mit Claude. Die Basics (Website, Datenmodell, Sicherheit, Rollenablauf) will er selbst verstehen und lernen.
- Kein Verkauf geplant. Keine Mehrkosten über das Pro-Abo hinaus.
- Regel für Claude: kleinste Lösung, die die Anforderung erfüllt; erst die Schnittstelle zeigen, dann die Implementierung; ein Modul pro Auftrag; Entscheidungen kurz begründen.
- Allgemeines Ziel: effizient arbeiten. Das Pro-Kontingent ist begrenzt, also verbraucht jede Aufgabe nur so viel wie nötig: kleine, klar umrissene Aufträge, das passende Modell je Aufgabe, nur der nötige Kontext (kurze CLAUDE.md, nur die relevanten Dateien), Limits für Durchläufe und Zeit und ein sichtbarer Verbrauch pro Lauf, um Verschwendung zu erkennen.

## 2. Getroffene Entscheidungen

- Claude Pro-Abo, keine API-Kosten. Sind die Limits aufgebraucht, wird später weitergearbeitet.
- Zugriff von überall über eigene Domain, Login mit E-Mail und Passwort. Passwort zurücksetzen und Einladungen per E-Mail über Resend (gebaut, Abschnitt 5 und 9).
- Rollen: Owner (genau einer, übertragbar), Superadmin, Admin, Nutzer (Rangregel, Abschnitt „Benutzerverwaltung“ und 11a, 4a). Keine Selbstregistrierung. Jeder Nutzer sieht und ändert nur seine eigenen Daten, und jeder verbindet sein eigenes Claude-Konto (Pflichtregeln in Abschnitt 3 und 6).
- Eine Installation pro Pi, mit Benutzerkonten. Andere nutzen entweder Janis’ Pi als Server mit eigener Claude-Anbindung oder installieren das Paket auf einem eigenen Pi. Janis’ Abo wird nie geteilt.
- Zuerst nur Claude. Andere KIs (z. B. ChatGPT) später als separate Anmeldung hinter einer gemeinsamen Schnittstelle. **Seit 14.11.2026 (live):** Mistral per API-Schlüssel für den Manager-Chat (Änderungsprotokoll, Eintrag `mistral`).
- **Mehrere KIs (15.11.2026):** Jede KI ist austauschbar und hängt hinter einem Adapter; der Hub hält Erinnerung, Regeln und Ablauf. Je Nutzer eine Standard-KI mit automatischem Rückfall auf seine nächste eigene KI. Zusatzkosten nur, wenn der Nutzer sie selbst einschaltet (Mistral: Pay-as-you-go).
- Programmiersprache Python; ein Wechsel nur, wenn JavaScript große Vorteile bringt.
- Eigene Struktur konsequent umsetzen, vorhandene Open-Source-Bausteine nutzen, wo sie passen.
- Tägliches Backup auf einen USB-Stick bzw. eine externe Platte, verschlüsselt (seit 11.11.2026 mit `tar` und `gpg` statt restic, siehe Abschnitt 9), zusätzlich Git-Spiegel auf GitHub. Struktur, Doku und offene Punkte haben höchste Priorität. Zurückrollen von Versionen gehört von Anfang an dazu.
- Zunächst ein bis zwei weitere Nutzer; bei Problemen wird reguliert.
- GitHub: privater Spiegel der Projekte, später auch zum Teilen mit Freunden.
- Modellwahl: Standard ist Sonnet 5.5 (gut genug für den Alltag, schont das Pro-Limit). Opus 5.5 nur gezielt für schwierige Aufgaben (Architektur, hartnäckige Fehlersuche, Prüfer), Haiku 5.5 für einfache, häufige Aufgaben (Zusammenfassungen, Commit-Texte). Umschalten in Claude Code mit /model.

## 3. Offener Kernpunkt: Anbindung des Abos

Soweit bekannt, lässt sich ein Abo nicht über Benutzername und Passwort an eine fremde Website anbinden, und die Restlimits sind nicht auslesbar. Der naheliegende Weg ohne API-Kosten:

- Auf dem Pi läuft Claude Code (Kommandozeile) eigenständig und unabhängig vom Mac, angemeldet mit dem eigenen Konto. Die Website startet es für die Agenten-Aufgaben und liest dessen Ausgabe.
- Jeder Nutzer meldet sein eigenes Claude Code an. Daten und Limits bleiben getrennt.
- Die Token-Anzeige auf der Startseite ist dann kein Abo-Restwert, sondern eine eigene Zählung: Der Verbrauch pro Lauf (Tokens, Dauer) wird aus der Ausgabe von Claude Code gelesen und pro Projekt summiert (Format in Phase 2 prüfen). Der Abo-Rest bleibt in den Claude-Einstellungen unter Nutzung; ob Claude Code ihn über einen Befehl wie /usage anzeigt, wird getestet.
- Vor dem Bau prüfen: Nutzungsbedingungen für den Einsatz in eigenen Tools, Verfügbarkeit im Pro-Plan, Betrieb auf dem Pi (Pi 4/5, 64-Bit-OS, Node.js-Anforderung).

Sonderregel für Swift (Entwurf): Swift-Code braucht Xcode und den Simulator und lässt sich nur am Mac bauen und testen. Der Pi bleibt Zentrale für Board, Rollen und Git. Für Swift-Aufgaben arbeitet Claude Code auf dem Mac im selben Git-Repo, der Pi übernimmt das Ergebnis per Git. Tests mit echtem iPhone und Pi meldet der Tester als „nicht prüfbar“. Die genaue Aufteilung wird vor Phase 2 festgelegt.

### Installation und Ersteinrichtung (Ziel)

- Wer das Paket (z. B. von GitHub) auf einen frischen Pi holt, soll möglichst nichts von Hand einrichten: ein Befehl lädt das Repo, ein Installationsskript installiert Docker, legt `/opt/agent-hub/` an und startet alles.
- Danach läuft die Einrichtung im Browser als Assistent: 1. Admin-Konto anlegen, 2. Verbindung nach außen (Cloudflare-Tunnel-Token einfügen), 3. Claude verbinden, 4. E-Mail-Versand einrichten.
- Nicht automatisierbar bleiben die Konten und Zugänge: Domain, Cloudflare, Claude, GitHub.
- Kein Anmelden per SSH auf dem Pi nötig. Alles läuft über die Webmaske per HTTPS.

### Claude-Anmeldung über die Weboberfläche (Ziel)

- Benutzername und Passwort von Claude gehen nie an den Pi. Die Anmeldung läuft über OAuth: Der Pi zeigt einen Anmelde-Link, der Nutzer bestätigt im Browser bei Claude und gibt den angezeigten Code oder Token in die Webmaske ein.
- Ablauf: Knopf „Mit Claude verbinden“, der Pi-Runner startet den Anmeldevorgang, die Maske zeigt den Link, der Nutzer bestätigt, Code oder Token geht zurück in die Maske, der Pi speichert ihn verschlüsselt pro Nutzer.
- Fallback: Token am Mac mit `claude setup-token` erzeugen und in die Maske einfügen. Auch dann ist kein SSH auf den Pi nötig.
- Risiko: Nach Fehlerberichten ist die Anmeldung ohne Bildschirm auf ARM64-Geräten wie dem Pi teils fehlerhaft, und Token laufen eventuell ohne automatische Erneuerung ab. Darum früh testen und in der Oberfläche den Status „Verbindung abgelaufen“ mit Knopf zum Erneuern anzeigen.
- Sicherheit: nur über HTTPS, Token verschlüsselt, nie in Logs oder im Git.

### Trennung der Claude-Konten (Pflichtregeln, Janis, 07.11.2026)

Jeder Nutzer verbindet sein eigenes Claude-Konto. Die Konten dürfen sich nie berühren: Wer ein Konto verbindet, bindet es nur für sich, und niemand benutzt je das Claude eines anderen mit. **Stand 14.11.2026:** gebaut, wie unten im Abschnitt „Claude-Anmeldung und Tokens, so gebaut“ beschrieben (Token aus `claude setup-token`, verschlüsselt pro Nutzer, Läufe nur mit Ticket). Es gilt, und die Tests von Runner und Hub prüfen es:

1. **Ein Konfigurationsordner pro Nutzer.** Jeder Nutzer bekommt seinen eigenen Ordner für die Claude-Anmeldung (z. B. `/data/claude/<user_id>/`, über `CLAUDE_CONFIG_DIR`/`HOME` des Prozesses). Es gibt nie ein gemeinsames Volume und kein gemeinsames `HOME` für mehrere Nutzer. Janis’ bestehende Anmeldung wird sein Nutzerordner, nicht der Standard für alle.
2. **Kein Rückfall.** Hat ein Nutzer kein Claude verbunden (oder ist die Verbindung abgelaufen), startet seine Aufgabe nicht und wartet mit dem Status „nicht verbunden“. Es gibt keinen Ersatz durch die Anmeldung eines anderen, auch nicht die des Owners.
3. **Ein Lauf sieht nur seinen Nutzer.** Jede Aufgabe läuft in einem eigenen Container oder Prozess, der nur zwei Ordner sieht: den Projektordner dieser Aufgabe und den Claude-Ordner dieses Nutzers. Weder die Ordner anderer Nutzer noch `hub.db`, `.env`, Backups oder der Tresor sind eingehängt. Zwischen zwei Läufen verschiedener Nutzer gibt es keinen geteilten Speicher, keine gemeinsame Arbeitskopie und keine Verbindung zwischen den Agenten.
4. **Der Nutzer kommt vom Server, nie vom Aufrufer.** Der Runner bekommt `user_id` und Projekt aus dem Aufgabendatensatz auf dem Server, nie aus einem Parameter, den ein Browser mitschicken kann. Schreibt ein Agent ins Board, dann mit `board.create_suggestion(user_id, project_id, kind, title)`; die Funktion prüft wie alle anderen, dass das Projekt diesem Nutzer gehört.
5. **Token nur verschlüsselt und nur für den Besitzer.** Verbindungsdaten liegen verschlüsselt pro Nutzer (`token.enc`, Schlüssel nur im Runner), und kein Lauf bekommt sie (nur ein Ticket). Weder Admins noch der Owner können sie anzeigen oder exportieren. Die Anzeige „Verknüpft“ und die Nutzungszählung hängen am Nutzer, nicht am Pi.
6. **Test.** Vor dem ersten Livegang der Anbindung kommt ein Test, der mit zwei Nutzern prüft: Der Lauf von B hängt nur den Ordner von B ein, ohne Verbindung von B startet nichts, und die Zählung von A bleibt bei A.

### Claude-Anmeldung und Tokens, so gebaut (14.11.2026)

Ziel von Janis: eine Anmeldung, die nicht abläuft, und Tokens, die weder der Betreiber des Servers noch ein Agent zu sehen bekommt. Vorbild war der Open-Source-Client Hermes (Nous Research): Er nimmt entweder den Token aus `claude setup-token` (`CLAUDE_CODE_OAUTH_TOKEN`) oder liest die Anmeldedatei von Claude Code und erneuert sie selbst. Das Zweite ist wackelig (ein Erneuerungs-Token gilt nur einmal, zwei Programme stoßen sich gegenseitig ab) und braucht eine vorgetäuschte Programmkennung; der Hub nimmt deshalb den ersten, offiziellen Weg (code.claude.com/docs/en/authentication, „Generate a long-lived token“).

1. **Verknüpfen:** Der Nutzer drückt in der Schublade „Verknüpfen“. Der Runner startet einen Wegwerf-Container mit `claude setup-token` (Heimordner nur im Arbeitsspeicher, Netz nur zu Anthropic). Die Seite zeigt den Link, der Nutzer bestätigt bei Claude und tippt den Code ein; der Code geht nur in das Terminal dieses einen Containers. Claude Code gibt danach einen **Token für ein Jahr** aus (`sk-ant-oat01-…`). Der Runner liest ihn aus dem Terminal, löscht den Container und vergisst die Ausgabe.
2. **Speichern:** Der Runner verschlüsselt den Token (Fernet aus dem Paket `cryptography`: AES-128-CBC mit HMAC-SHA256; keine eigene Kryptografie) und legt ihn als `/opt/agent-hub/claude/<Nutzer-Nr.>/token.enc` ab (Besitzer root, Ordner 0700, Datei 0600, außerhalb von `data/`). Der Schlüssel `HUB_TOKEN_KEY` steht in der `.env` und wird **nur** an den Runner gegeben; Web-Dienst, Egress-Proxy und Läufe kennen ihn nicht. Klartext liegt nie auf der Karte, nie in der Datenbank, nie in einem Log. Die Dateien der alten Anmeldung im Ordner werden dabei gelöscht.
3. **Benutzen:** Ein Lauf (Manager-Chat, später die Agenten) bekommt **nie** den Token und keinen Claude-Ordner. Er bekommt ein **Ticket** (`hubrun-` und 43 Zufallszeichen) als `CLAUDE_CODE_OAUTH_TOKEN` und schickt alle Anfragen an `http://egress:3130` (`ANTHROPIC_BASE_URL`, nur im internen Agenten-Netz erreichbar; `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, damit Claude Code sonst nichts zu Anthropic schickt). Der Runner legt für die Dauer des Laufs den Token unter dem SHA-256 des Tickets in einen Ordner im **Arbeitsspeicher** (tmpfs-Volume `tickets`), den nur Runner und Egress-Proxy einhängen. Der Gateway im Egress-Proxy prüft Pfad (`/v1/…`), Länge und Ticket, setzt den echten Token ein und schickt die Anfrage per TLS an `api.anthropic.com`; die Antwort fließt unverändert zurück. Nach dem Lauf löscht der Runner die Ticket-Datei (spätestens nach einer Stunde zählt sie ohnehin nicht mehr, beim Start des Runners werden alle gelöscht).
4. **Ablauf:** Der Hub merkt sich das Ende (`claude_connections.expires_at`, ein Jahr nach dem Verknüpfen). Ab 30 Tagen vorher zeigt die Schublade „Läuft bald ab · Erneuern“; Erneuern meldet neu an, der alte Token arbeitet weiter, bis der neue da ist (klappt es nicht, bleibt der alte). Lehnt Anthropic den Token ab (widerrufen, abgelaufen), springt die Schublade sofort auf „Abgelaufen · Erneuern“.
5. **Trennen:** löscht den Ordner mit `token.enc` (Runner, `handle_wipes`). Den Token selbst kann man zusätzlich bei Claude unter den Einstellungen widerrufen.
6. **Abgelaufen oder abgelehnt (Janis, 14.11.2026):** Der Runner löscht den gespeicherten Token von selbst (`/runner/expired`, `handle_expired`), auch die Dateien der alten Anmeldung; die Schublade zeigt weiter „Abgelaufen · Erneuern“.
7. **Wenn das Verknüpfen scheitert,** schreibt der Runner das Ende der Terminal-Anzeige ins Protokoll, jede lange Zeichenfolge (Token, Code, Link) durch ihre Länge ersetzt (`login.redacted_tail`).

**Was das schützt:** Ein Agent kann den Token nicht lesen und nicht ins Internet bringen, auch nicht mit offenem Internet und Code: Im Lauf gibt es ihn nicht, das Ticket gilt nur im Agenten-Netz und nur bis zum Ende des Laufs. Andere Nutzer kommen nicht an fremde Tokens (eigener Ordner, kein gemeinsames Volume, kein Rückfall auf ein anderes Konto). Weder Admins noch der Owner haben in der Oberfläche einen Weg, einen Token zu sehen oder auszulesen. Eine Kopie von `data/` oder ein falsch eingehängter Ordner verrät nichts (verschlüsselt, Schlüssel nur im Runner). Das Backup enthält `token.enc` und `.env`; es ist selbst mit einem eigenen Passwort verschlüsselt.

**Grenze (ehrlich):** Wer root auf dem Pi ist, kann technisch alles, was der Runner kann, also auch entschlüsseln: Ein Dienst, der ohne den Nutzer arbeiten soll, braucht den Schlüssel auf derselben Maschine. Gegen den Betreiber selbst schützt nur Vertrauen (oder ein eigener Pi des Freundes). Was die Lösung garantiert: kein Weg über die Oberfläche, nichts im Klartext auf der Karte oder im Backup, nichts in einem Lauf.

Umbau: keiner.

**Schlüssel, so gebaut (gleiche Struktur wie bei Claude):**
1. **Verknüpfen:** Zahnrad → Pfeil → Mistral → „Verknüpfen“ öffnet einen Dialog (Link zur Schlüsselseite, Passwortfeld). Der Schlüssel geht per `POST /ai/mistral/connect` an den Web-Dienst, liegt dort **nur einige Minuten im Arbeitsspeicher** (`ai_link._keys`, nie in der Datenbank, nie im Log) und wird dem Runner **einmal** übergeben (`/runner/keys/claim`).
2. **Prüfen und speichern:** Der Runner fragt `GET https://api.mistral.ai/v1/models` (`runner/mistral.py`) und legt den Schlüssel **verschlüsselt** ab: `tokens.ProviderKeys`, Fernet mit demselben `HUB_TOKEN_KEY` wie die Claude-Tokens, Datei `/opt/agent-hub/claude/keys/mistral/<Nutzer-Nr.>.enc` (Ordner 0700, Datei 0600, root). Eigener Unterordner `keys/`, damit Trennen oder Ablauf von Claude ihn nicht mitlöscht; im nächtlichen Backup mit dem Claude-Ordner.
3. **Benutzen:** Kein Lauf bekommt den Schlüssel und kein Container entschlüsselt selbst (Janis’ Vorschlag „der Container entschlüsselt“ wurde zugunsten derselben Lösung wie bei Claude verworfen, damit Code im Lauf den Schlüssel nie lesen kann). Der Lauf bekommt ein **Ticket**; das Ticket **nennt seine KI** und gilt nur an deren Gateway im Egress-Proxy: Claude Port 3130 → api.anthropic.com, **Mistral Port 3131 → api.mistral.ai**. Der Gateway setzt den echten Schlüssel ein.
4. **Abgelehnt:** Antwortet Mistral mit 401, löscht der Runner den Schlüssel und die Schublade zeigt „Schlüssel abgelehnt · Erneuern“; ein neuer Schlüssel, der nicht klappt, lässt den alten weiterarbeiten (`ai_connections.previous`). **Wichtig:** Das Mistral-Gateway beantwortet ein unbekanntes Ticket mit **502**, nicht 403, weil Vibe 403 als falschen Schlüssel liest und der Runner ihn sonst löschen würde (live gefunden 15.11.2026). Eine Störung beim Hub kostet nie den Schlüssel.
5. **Trennen / Konto gelöscht:** Zeile auf `wipe`, der Runner löscht die Datei (`/runner/keys/wipes`); `ai_connections` hat absichtlich keinen Fremdschlüssel, damit auch die Dateien gelöschter Konten gelöscht werden.

**KI je Rolle (22.11.2026, `polish-ui`):** Jede Rolle kann ihre eigene KI haben (`agent_settings` `ai.role.<rolle>`, gewählt über die Pillen im Rollen-Tab; `agents.role_provider_in`). Wird am Projekt gearbeitet (`active`: eine Aufgabe in `workflow.STAGES` oder der Manager-Chat in den letzten 10 min), kommt alle 2 min eine neue Runde (`ACTIVE_GAP`), ohne Tagesgrenze; ruhige Projekte behalten `MIN_GAP` (6 h), `URGENT_GAP` (20 min nach einem wichtigen Ereignis) und `DAILY_MAX`. „Neu schreiben“ des Nutzers hat keine Grenze (`statusnote.request`); ist schon eine Runde unterwegs, wartet der Knopf auf diese. Eine Runde ist ein eigener Chat-Auftrag (`kind = 'status'`, günstigstes Modell, ohne Werkzeuge) und braucht keinen freien KI-Platz, läuft also neben den Agentenläufen; eine Frage des Nutzers geht ihr aber vor (`ORDER BY kind = 'status', id`). Die Kachel holt sich alle 20 s neu (`GET /projects/{id}/status/tile`, Zahlen ohne KI), während einer Runde alle 4 s; der Pfeil dreht sich und ist gesperrt, solange eine Runde unterwegs ist (`statusnote.writing`).

**Reihenfolge (21.11.2026, `bug-lists`):** ordnet sich selbst (`aichoice.ranked_in`): die Standard-KI, die vorher Standard war (`agent_settings` `ai.previous`), die übrigen verknüpften in der Reihenfolge des Katalogs; so steht sie in der Schublade (danach die nicht verknüpften) und so wird beim Ausweichen gefragt (eine pausierende KI zuletzt). **Fehlerlisten:** Mehrere Mängel in einer Nachricht werden je ein eigener Fehler, bis zu 12 je Antwort.

**Standard-KI und Rückfall (`web/app/aichoice.py`, 15.11.2026):** Jeder Nutzer hat eine Standard-KI (`agent_settings` Schlüssel `ai.default`; ist sie nicht mehr verknüpft, gilt die erste verknüpfte in der Reihenfolge von `catalog.PROVIDERS`). Chat und Agentenläufe nutzen sie; kann sie nicht (nicht verknüpft, abgelaufen, Kontingent leer), übernimmt **automatisch** die nächste **eigene** KI, mit Hinweis unter der Antwort. Modell und Stufe gelten je Rolle **und** je KI (`model.<rolle>.<anbieter>`). Der Prüfer nimmt eine andere KI als der Programmierer, wenn zwei verknüpft sind. **Anleitung für Nutzer:** `ANLEITUNG-MISTRAL.md` (im Repo und im iCloud-Ordner; bei Änderungen an Schublade oder Mistral mit anpassen).

### Agentenschleife, Testbrowser und Grenzen (Janis, 21.11.2026, `robust-loop`)

> **Stand 22.11.2026 (`chain`):** Die Kette ist neu gebaut (KONZEPT-AGENTEN.md 10). Überholt sind hier: die Hinweise zur Umgebung unter „Wartet auf dich“ (jetzt Einträge in „Für dich“), „Weniger Freigaben“ (es gibt keine Freigabe mehr) und das Zeitlimit Agentenlauf (jetzt Stillstand und Höchstdauer). Fehlerarten, Ausweichen, Doppelte, Code-Download, Testbrowser und die übrigen Grenzen gelten weiter.

Anlass: ein Test mit einem einfachen Taschenrechner. 45 Punkte auf dem Board, 37 von der Agentenkette selbst, viele doppelt (sechsmal „Anzeige ans Ende scrollen“), viele über die Umgebung (Node, Browser, leeres `/work`); sechs Aufgaben warteten auf Freigabe; als Claudes Kontingent leer war, sprang ChatGPT nicht ein; die Agenten konnten die Oberfläche nicht ansehen.

- **Fehlerarten** (`web/app/failures.py`): server, plan, auth, limit, timeout, steps, other, aus den echten Meldungen (Claude Code „You've hit your 5-hour limit · resets …“, „usage limit reached“, „out of extra usage“; Codex „try again in 2 days“, 429; Mistral „rate limit exceeded“; Anmeldung „OAuth token has expired“, „Invalid API key“). Chat und Läufe benutzen dieselbe Stelle.
- **Ausweichen:** Nach `auth` oder `limit` erst der API-Schlüssel derselben KI (wenn erlaubt), dann die nächste eigene KI, die den Auftrag noch nicht versucht hat (`chat_messages.tried`, neu `agent_runs.tried`); nie zurück. Eine KI mit leerem Kontingent **pausiert** (`aichoice.rest`, Einstellung „Leeres Kontingent“, Standard 30 Minuten): sie steht so lange am Ende der Reihenfolge, wird aber noch gefragt, wenn keine andere kann.
- **Was aufs Board kommt:** Der Programmierer erledigt alles zur Aufgabe Gehörende (Randfälle, Meldungen, Aussehen, kleine Fehler im berührten Code). Tester und Prüfer melden Funde an der Aufgabe als Ergebnis (nicht bestanden, Einwände), die Runde geht zurück. Eine Rolle darf nur einen **Fehler außerhalb** der Aufgabe (sofort unter „Fehler“) und eine **neue Funktion** (wartet auf dein Ja) anlegen, höchstens drei je Lauf; eine „Verbesserung“ von einer Rolle verwirft der Hub. Der Manager zerlegt Wünsche ohne eigenen Feinschliff-, Aufräum- oder Nur-Test-Schritt.
- **Umgebung:** Fehlt einer Rolle etwas (Programm, Browser, Datei, Recht), meldet sie es mit `<env>`. Das wird ein **Hinweis** unter „Wartet auf dich“ („Tester meldet: In der Umgebung fehlt etwas“, ein Knopf „Erledigt“), geht an keine KI und nie aufs Board.
- **Doppelte** (`reply.similar`): gleiche bedeutungstragende Wörter (Füllwörter weg, Wörter nach den ersten fünf Buchstaben, Zahlen immer, verschiedene Zahlen heißen verschiedene Schritte), mindestens zwei gemeinsame und 60 % des kürzeren Texts. Für Board-Punkte (neuer Kontext wird an den bestehenden Punkt gehängt) und offene Fragen. Fragen einer Aufgabe verschwinden, wenn sie fertig oder abgebrochen ist.
- **Weniger Freigaben** (`agents._auto_approve`): Eine saubere Aufgabe (Prüfer ohne Einwand, nichts von Hand zu prüfen, Tests nicht rot, keine offene Frage) führt der Hub selbst zusammen, nach der Selbstständigkeit des Managers: „Selbstständig“ jede, „Fragt bei Großem“ (Standard) Fehler und Verbesserungen, „Fragt bei allem“ keine. Eskalationen und neue Funktionen warten weiter.
- **Code-Download** (`web/app/exports.py`, Kachel „Code“ im Programmierer-Tab): „Hauptstand herunterladen“ und „Stand der Aufgabe herunterladen“. Der Hub legt einen Auftrag an, der Runner packt mit `git archive` und schickt die ZIP-Datei roh (`/runner/exports/{id}`), die Seite fragt nach und lädt herunter. Gehalten eine Stunde; mit Projekt und Konto weg. Größe als Einstellung.
- **Testbrowser** (`runner/hub_browser.js`, in allen drei Lauf-Images: Chromium aus Debian, `playwright-core` 1.52.0): `hub-browser index.html --click "#seven" --fill "#field=12" --press Enter --shot`. Stellt `/work` über einen eigenen kleinen Server im Container bereit (nur `127.0.0.1`), führt die Schritte der Reihe nach aus, gibt Titel, sichtbaren Text, Konsolenfehler und fehlende Dateien mit Adresse aus und legt Bildschirmfotos in `/work/.hub-shots/` (nie im Commit). Kein Internet. Das Paket nennt ihn Programmierer und Tester, wenn er eingeschaltet ist. Am Pi unter Laufbedingungen (480 MB, schreibgeschützt, ohne Rechte, ohne Netz) erprobt: etwa 30 s je Aufruf.
- **Grenzen eines kleinen Servers** (`serversettings.CHOICES`, Verwaltung → System, Owner und Superadmin): Arbeitsspeicher je Lauf (480 MB … 8 GB), Prozessoren (1 … 8), Prozesse (256 … 4096, Standard 512 wegen des Browsers), Dateien je Lauf (200 MB … 5 GB), Zeitlimit Agentenlauf (20 … 120 min; Aufgabe = höchstens sechs Läufe, mindestens 2 h; Tests ein Viertel, mindestens 5 min), Zeitlimit Chat (3 … 20 min), Testbrowser an/aus, Code-Download (10 … 500 MB), Pause bei leerem Kontingent. Jeder Auftrag trägt sie (`limits`), der Runner prüft sie selbst (`launcher.checked`) und setzt sie in den `docker run` (`launcher.apply_limits`, nur vor dem Image). Durchgesehen und bewusst fest geblieben: Längen von Titeln, Berichten, Diffs und Kontext (Tokens), Anzahl der Fragen und Punkte, Sperren bei falschen Passwörtern, Gateway-Grenzen (Schutz).

### API-Schlüssel neben dem Abo (Janis, 21.11.2026, `api-option`)

- **Warum:** Abo und API liefern dieselben Modelle in derselben Qualität bei gleichem Tokenverbrauch. Der Schlüssel kostet nach Verbrauch, hat dafür keine Wochengrenze, läuft nicht ab, bietet alle Modelle und erlaubt Automatisierung sauber nach den Nutzungsbedingungen. Darum nur als Option, die der Nutzer selbst einstellt, und ohne festen Preis in der Oberfläche („Kann Zusatzkosten verursachen. Prüfe die Preise bei deinem Anbieter und setze dort eine Ausgabengrenze.“): ändern sich die Preise, muss am Hub nichts geändert werden.
- **Für wen:** Claude und ChatGPT (`credentials.API_FOR`). Mistral hat ohnehin nur einen Schlüssel, die weiteren KIs auch.
- **Einstellungen je Nutzer und KI** (`agent_settings` `api.<anbieter>.mode|scope|daily`, `web/app/credentials.py`): **Modus** `fallback` (Standard: erst wenn das Abo nicht antworten kann, z. B. Kontingent aufgebraucht oder Anmeldung verloren), `always` (der Schlüssel statt des Abos, das Kontingent bleibt), `off` (der Schlüssel bleibt gespeichert, wird aber nie benutzt); **Bereich** `all`, `runs` (nur Agentenläufe), `chat` (nur Manager-Chat und kleine Aufträge des Hubs); **Tagesgrenze** in Tausend Tokens (0 = ohne Grenze, höchstens 1 000 000); darüber wartet der Schlüssel bis Mitternacht.
- **Verbindung:** Der Schlüssel ist eine eigene Verbindung (`ai_connections` `claude-api`, `chatgpt-api`), geprüft vom Runner (`runner/apikeys.py`: Anthropic `GET /v1/models` mit `x-api-key`, OpenAI `GET /v1/models`), verschlüsselt gespeichert wie die anderen (`tokens.ProviderKeys`), nie wieder angezeigt; bei klarer Ablehnung (401) gelöscht.
- **Welcher Weg:** `credentials.order` gibt je Auftrag die erlaubten Wege („plan“, „api“) in ihrer Reihenfolge; der erste wird beim Abholen gesetzt und steht am Auftrag (`chat_messages.credential`, `agent_runs.credential`), damit die Tagesgrenze ihn zählt (`spent_today`, nur „api“). Scheitert das Abo am Kontingent oder an der Anmeldung, geht derselbe Auftrag mit dem Schlüssel weiter (`next_way`), **bevor** die nächste KI einspringt. Gewechselt wird **nur vom Abo zum Schlüssel, nie zurück**: so kann kein Auftrag zwischen beiden kreisen. Eine KI, die nur einen Schlüssel hat, gilt als verknüpft (`aichoice.connected_in`).
- **Gateways:** Die Läufe bekommen weiter nur ein Ticket. Claude Code bekommt es als `ANTHROPIC_API_KEY` und sendet es als `x-api-key`; das Gateway 3130 setzt den echten Schlüssel als `x-api-key` ein. Codex bekommt für den Schlüssel einen eigenen Anbieter mit `env_key` und `/v1`; das Gateway 3133 schickt einen Schlüssel nur an `api.openai.com` (`/v1/responses`, `/v1/models`, ohne Konto-Kopf), das Abo nur an `chatgpt.com/backend-api/codex`. Nie gemischt: das Ticket eines Abos gilt nur in seiner Hülle, das eines Schlüssels nur bloß (Test in `runner/test_egress.py`).
- **Oberfläche:** zweigeteilter Dialog (DESIGN.md 4, „Verknüpfen-Dialog in zwei Hälften“), in der Schublade unter der KI die Zeile „API: <Modus>“, sobald ein Schlüssel verknüpft ist. Routen `GET|POST /ai/{anbieter}/api`, `POST /ai/{anbieter}/api/remove`.

### Weitere KI: allgemeine Anbindung (Janis, 20. und 21.11.2026, `own-ai`, `more-ais`)

Falsche Angaben meldet der Dialog am Feld (`field`: `endpoint`, `model`, `key`, `home`, `full`).

Bis dahin „Kommt später“, ohne Knopf und ohne „i“; über ihre OpenAI-kompatible Adresse gehen sie schon jetzt als weitere KI.
- **Netz des Servers: freigegebene Adressen (Janis, 21.11.2026, `ai-manage`; ersetzt den Schalter „KI im Heimnetz“ vom selben Tag):** Eine Adresse im Netz des Servers (10/8, 192.168/16, Tailscale 100.64/10, Namen ohne Punkt oder mit lokaler Endung wie `.local`, `.fritz.box`) und jede Adresse ohne https nutzt eine weitere KI nur, wenn der **Owner** sie in der Verwaltung freigegeben hat (Zeile „Freigegebene Adressen“, Dialog mit Liste und Formular; Tabelle `net_addresses`, `web/app/netaddresses.py`): **Host und Port genau**, für **alle Konten oder ein Konto**, mit Notiz, höchstens 50. Nie freigebbar: der Server selbst (127/8, `localhost`) und Docker (172.16/12). So kann Janis auch einem Kollegen eine KI in seinem Netz geben. Das Ticket eines Auftrags trägt `lan` nur bei freigegebener Adresse (`ai_link.route_in`, `take_keys`); nur dann verbindet das Gateway 3132 zu einer Adresse im Netz, und nur zu diesem Host. Entfernen gilt ab dem nächsten Auftrag; ein gelöschtes Konto nimmt seine Einträge mit. Adressen im Internet brauchen keine Freigabe. Verworfen: der Schalter für das ganze Netz (öffnet zu viel und nur für den Owner) und ganze Adressbereiche (ein Host mit Port ist enger). Superadmins sehen die Zeile nicht.
- **Offen:** das Modell aus `GET /models` der Adresse als Auswahl statt zum Eintippen; Bilder für die weiteren KIs; Werkzeuge je KI auf `/admin` umschaltbar. Noch nie echt gelaufen (keine solche API verbunden).

### Tresor für Zugangsdaten (Ziel)

- Janis lädt Zugangsdaten (SSH-Schlüssel, Passwörter, Tokens) über die Weboberfläche in einen Tresor. Agenten können sie nie lesen, nur nutzen lassen.
- Prinzip Vermittler: Der Agent bittet den Vermittler um eine Aktion (z. B. „auf dem Gerät roadster `git pull` ausführen“). Der Vermittler holt das Geheimnis, führt die Aktion selbst aus und gibt nur das gefilterte Ergebnis zurück. Das Geheimnis verlässt den Vermittler nie.
- Der Vermittler läuft als eigener Container. Der Agenten-Container hat weder Zugriff auf den Tresor-Ordner noch auf die Schlüssel (getrennte Volumes und Netze).
- Pro Zugang: Name, Typ, erlaubte Aktionen (Allowlist) und ob eine Freigabe durch Janis nötig ist. Beispiel: Zugang „roadster“ erlaubt nur `git pull` und den Neustart des Dienstes.
- Auf der Gegenseite ein eigener Benutzer mit Schlüssel-Login und eingeschränkten Rechten, nie Root. Schlüssel sind besser als Passwörter.
- Ausgaben werden gefiltert (Geheimnisse geschwärzt), jede Nutzung steht im Aktivitätsprotokoll.
- Verschlüsselung mit einer bewährten Bibliothek, keine eigene Kryptografie. Hauptschlüssel nicht neben den Daten, Entsperren nach dem Start per Passwort in der Weboberfläche. Später optional Vaultwarden als fertige Lösung.
- Grenze: Läuft eine Aktion in einer freien Shell mit dem Geheimnis, könnte ein Agent es über Umwege auslesen. Darum nur freigegebene Aktionen, keine freie Shell.

## 4. Architektur (Entwurf)

- Hardware: Raspberry Pi 4 mit micro SD (später externe USB SSD). Betriebssystem: Raspberry Pi OS Lite 64-Bit (Debian für den Pi, mit passenden Treibern).
- Zugriff: Cloudflare Tunnel statt offener Router-Ports, HTTPS inklusive. Tailscale bleibt nur Alternative für privaten Zugriff, weil es auf jedem Gerät eine App braucht.
- Web: kleines Backend mit SQLite als Datenbank, schlichtes Frontend. Konkreten Stack vor dem Bau festlegen.
- Agenten laufen in einem Container, jede Aufgabe in einem eigenen Git-Branch.
- Paketierung: Docker Compose, damit Freunde es mit wenigen Befehlen installieren.

### Speicher: SD jetzt, SSD später

- Ziel: das ganze Betriebssystem plus Daten auf einer USB-SSD, nicht nur die Daten. Datenbank, Docker und Git schreiben viel, SD-Karten verschleißen dabei schneller und fallen oft ohne Vorwarnung aus.
- Zum Start reicht die SD-Karte (mindestens 32 GB, Markenkarte), solange keine wichtigen Daten darauf liegen. Das tägliche Backup auf die externe SSD gilt ab Tag eins.
- Der Umzug ist unkompliziert, wenn alles unter `/opt/agent-hub/` liegt: Raspberry Pi OS per Raspberry Pi Imager frisch auf die SSD schreiben, Docker installieren, den Ordner zurückkopieren, `docker compose up -d`. Die SD-Karte bleibt unverändert als Rückfallebene.
- Der Pi 4B muss dafür von USB booten können. Die Bootreihenfolge wird in `raspi-config` gesetzt, bei älterer Firmware zuerst aktualisieren.
- Größe: 120 GB reichen, 240 GB geben Luft für Dateiablage und Repos. Die Backup-SSD mindestens gleich groß, Markenmodell mit USB-3-Gehäuse.

### Domain und Kosten

- Eine Domain kostet jährlich, nicht monatlich. Eine .com liegt 2026 laut Vergleichsseiten bei etwa 10–11 USD pro Jahr (Cloudflare, Porkbun, Spaceship). Entscheidend ist der Verlängerungspreis, nicht das Lockangebot im ersten Jahr.
- Geplante Domain: janis-home.de. Cloudflare Registrar bietet .de soweit bekannt (noch) nicht an, vor dem Kauf auf der TLD-Liste prüfen. Dann: Domain bei einem Registrar kaufen, der .de anbietet, und nur die Nameserver auf Cloudflare stellen (DNS und Tunnel). Das Dashboard läuft unter einer Subdomain wie hub.janis-home.de, damit die Hauptdomain für andere Dienste frei bleibt.
- Cloudflare Tunnel und Tailscale sind für den privaten Gebrauch soweit bekannt kostenlos. Konditionen vor dem Start prüfen.
- Laufende Kosten: nur die Domain. Dazu einmalig eine SSD.

### Container-Aufbau auf dem Pi

- Direkt auf dem Pi (Host): Raspberry Pi OS Lite, Docker Engine mit Docker Compose (aus der offiziellen Docker-Paketquelle), Git, SSH. Sonst nichts.
- In Containern, gestartet über eine Datei `compose.yml`: `web` (Backend und Oberfläche, SQLite-Datei im Datenordner), `tunnel` (cloudflared), `runner-pi` (Claude Code und Git, arbeitet nur im Projektordner), optional `backup` (restic).
- Ordner auf dem Pi: `/opt/agent-hub/` mit `compose.yml`, `.env` (Geheimnisse, nie im Git), `data/` (SQLite, Dateiablage), `workspaces/` (ein Git-Repo je Projekt), `backups/`.
- Der Claude-Login des Runners liegt in einem eigenen Container-Volume und nie im Git.

### Zugriff der Agenten auf Geräte (SSH)

- Claude Code läuft als lokales Programm auf dem Pi (bzw. Mac-Runner), nicht als Cloud-Sitzung. Es kann daher alles, was eine Shell auf diesem Rechner kann, auch `ssh` zu anderen Geräten im Heimnetz.
- Die Einschränkung „kein SSH, nur lokal“ betrifft Claude Code im Web (Sitzungen in Anthropics Cloud). Die nutzt der Hub nicht.
- Agenten sprechen nicht direkt miteinander: Der Hub reicht Ergebnisse weiter (Branch, Berichte, Datenbank).
- Geräte per USB (z. B. ESP32, Arduino): Runner auf dem Rechner, an dem das Gerät hängt, oder USB an den Container durchreichen.
- Geräte außerhalb des Heimnetzes: per VPN, siehe unten.

### Geräteliste und Netzwege (entschieden 07.11.2026, Janis)

- **Das Heimnetz bleibt für Agenten gesperrt.** Läufe haben keine Route dorthin; ihr einziger Weg nach draußen ist der `egress`-Proxy (KONZEPT-AGENTEN.md 6a). Verworfen: das Heimnetz pauschal freigeben. Ein per Webseite gelenkter Agent (Prompt-Injection) säße dann im Netz und erreichte alles ohne Passwort: Router, Drucker, Smart Home, Dienste des Pi, Geräte am Fahrzeug, später auch Agenten fremder Nutzer in Janis’ Netz. Ein SSH-Schlüssel schützt davor nicht, denn der Agent sitzt schon drin.
- **Geräteliste im Manager:** Der Nutzer trägt den Hostnamen eines Geräts ein. Der Hub (der Vermittler, nie der Agent) löst ihn im Netz auf, liest die Gerätedaten (Adresse, SSH-Port, Hostschlüssel) und führt das Gerät nach Freigabe durch den Nutzer in der Liste der freigegebenen Geräte. Optional wird dem Gerät ein SSH-Schlüssel im Tresor zugeordnet. Der Agent erreicht Geräte nur über den Vermittler; Schlüssel gelangen nie in einen Lauf-Container.
- **Auflagen** (Vorschlag von Claude, von Janis noch nicht ausdrücklich bestätigt, aber Teil der Mandantentrennung): ein Gerät gehört genau einem Nutzer und einem Projekt (Fall in `test_isolation.py`); die aufgelöste Adresse wird gespeichert und bei jeder Verbindung geprüft (kein Umlenken per DNS); der Hostschlüssel wird beim Eintrag gemerkt und danach geprüft; pro Gerät eine Liste erlaubter Befehle (bei Testgeräten weiter gefasst); Hardware am Fahrzeug (Roadster, Heizung, Relais, Bordnetz) steht nie auf der Liste, das schaltet Janis vor Ort.
- **Geräte in fremden Netzen** (z. B. beim Kollegen zu Hause): per VPN, sternförmig mit dem Pi in der Mitte. Isolation, wie von Janis festgelegt: (1) Jeder Kollege hat seine **eigene** VPN-Verbindung zum Pi, und der Pi leitet **nicht** zwischen den Verbindungen weiter, damit Kollege A und Kollege B einander nie erreichen. (2) Der Pi darf zum Gerät nur per SSH (Port 22), das Gerät und die Verbindung dürfen weder ins Netz des Pi noch ins restliche Netz des Kollegen. Umgesetzt mit Firewall-Regeln am Pi (Weiterleiten verboten, einzige Ausnahme Pi zu Gerät Port 22) und am Gerät des Kollegen (nur Pi, nur Antworten).
- **VPN-Technik (Claude auf Janis’ Auftrag zu prüfen, Stand 07.11.2026 recherchiert): Tailscale.** Harte Vorgabe von Janis: **Auf der Fritzbox wird kein Port geöffnet.** Selbst gehostetes Headscale scheidet damit aus: Nach seiner Dokumentation läuft es hinter Cloudflare Tunnel nicht (Cloudflare reicht die nötigen WebSocket-POSTs nicht durch), und sein eingebauter Relay-Dienst braucht UDP 3478 öffentlich erreichbar. Es bräuchte also offene Ports oder einen zusätzlichen Server im Internet. Tailscale verbindet nur ausgehend (NAT-Durchdringung, bei Bedarf Relay über Tailscales Server), ohne offenen Port. Zugriffsregeln: Geräte der Kollegen bekommen ein Etikett (Tag) und werden mit einem Einmal-Schlüssel des Owners aufgenommen, die Kollegen brauchen kein eigenes Tailscale-Konto; Regel „Hub darf zu Gerät Port 22“, alles andere ist verboten (Standard von Tailscale), damit sind Kollegen untereinander und Geräte zum Netz hin getrennt. Kostenloser Tarif nach Tailscales Preisseite: bis 6 Nutzer, unbegrenzt Geräte, bis 50 Etikett-Geräte (frühere Quellen nennen 3 Nutzer; die Preisseite gilt). **Nachteile:** Tailscale (Drittanbieter) verwaltet die Zugangsdaten der VPN-Knoten und sieht Metadaten, nicht den Verkehr; der kostenlose Tarif ist nur für nicht gewerbliche Nutzung gedacht. **Vor dem Bau zu prüfen:** ob die Etiketten mit den drei „ACL-Gruppen“ des kostenlosen Tarifs auskommen, die Nutzungsbedingungen, und optional Tailnet Lock (Knoten nur mit Signatur des Owners). Verworfen: WireGuard mit offenem Port (Fritzbox), Headscale (siehe oben), umgekehrter SSH-Tunnel (mehr Eigenbau, keine Regeln pro Gerät).

- **KIs in fremden Netzen (Janis, 21.11.2026, später, noch nichts gebaut):** Eine KI beim Kollegen zu Hause (z. B. Ollama auf seinem Rechner) erreicht der Hub heute nur, wenn sie öffentlich erreichbar ist (eigener Tunnel mit https). Später derselbe Weg wie für Geräte: der Kollege verbindet sich mit eigenem Tailscale-Zugang zum Pi (sternförmig, keine Weiterleitung zwischen Kollegen, ACL je Kollege nur zu seinen eigenen Adressen), seine KI bekommt eine Adresse aus 100.64/10. Was dann zu bauen ist: (1) die Tailscale-Adresse seiner KI trägt der Owner als freigegebene Adresse nur für dieses Konto ein (gibt es seit 21.11.2026, `netaddresses.py`); (2) das Gateway 3132 prüft beim Verbinden, dass die aufgelöste Adresse zum freigegebenen Host gehört (heute: `lan` im Ticket nur bei freigegebener Adresse); (3) Test in `test_isolation.py`, dass Kollege A die Adressen von Kollege B nicht nutzen kann. Vorher: Tailscale auf dem Pi einrichten (kein offener Port auf der Fritzbox), ACLs schreiben, Dokumentation für den Kollegen.

### Mac-Integration: lokaler Runner

- Ein Browser darf keine Programme auf dem Mac starten, und ein offener Mac-Port wäre ein Risiko. Darum läuft auf dem Mac ein kleines Programm, der Runner. Er baut selbst eine Verbindung zum Pi-Server auf (nur ausgehend) und braucht **keine eigene Anmeldung oder Kopplung** (entschieden 07.11.2026, Janis): Die Anmeldung im Hub gilt als Verifikation. Der Nutzer drückt in der Website den Knopf; der Hub erzeugt ein kurzlebiges Einmal-Ticket für genau diesen Nutzer und diese Aufgabe, der Browser übergibt es über einen eigenen Link (`agenthub://`) an das Mac-Programm, das es beim Hub gegen die Aufgabe eintauscht. Das Ticket bedient der Nutzer nie. Das Mac-Programm (Plugin) muss einmal installiert sein und ist noch zu bauen. Verworfen: Kopplung per Code in den Einstellungen.
- Bei passenden Aufgaben (z. B. Swift) zeigt die Website den Knopf „Lokale Ressourcen verwenden“, sobald ein Mac-Runner online ist. Ist der Mac aus, steht dort „Mac nicht verbunden“ und die Aufgabe wartet.
- Ablauf: Runner holt das Repo, startet Claude Code auf dem Mac (Xcode, Simulator), schickt das Ergebnis zurück und meldet Status und Ergebnis an die Website.
- **Rückgabe ins Projekt (Janis, 07.11.2026: muss ins Projekt einfließen):** Der Mac erreicht den Pi nicht per Git oder SSH (kein offener Port), alles läuft über den Hub per HTTPS, ausgehend, mit dem Einmal-Ticket. (1) **Holen:** Der Hub gibt dem Mac das Repo als Git-Bundle (Stand der Aufgabe). (2) **Zurück:** Der Mac lädt am Ende **ein Git-Bundle mit genau dem Branch dieser Aufgabe** hoch. Der Hub prüft es (Größenlimit, nur dieser eine Branch, Basis ist der bekannte Stand, Branchname vom Hub vorgegeben, nie vom Mac), holt es per `git fetch` aus dem Bundle in das Projekt-Repo und läuft dann in der gewohnten Kette weiter (Prüfer, Freigabe durch den Nutzer, Merge nach `main`, Manager führt die Doku nach), genau wie nach einem Lauf auf dem Pi. (3) **Ergebnisse:** Der Mac meldet die letzte Zeile `RESULT: …` und den Bericht als Daten, wie die Läufe auf dem Pi. (4) **Abbruch:** Kommt kein Ergebnis (Mac aus oder Verbindung weg), läuft das Ticket ab, die Aufgabe steht wieder auf „wartet auf Mac“, Teilergebnisse gelten nicht. (5) **Hat sich `main` inzwischen geändert,** löst der Merge bei der Freigabe das auf (Modul „Worktrees und Merge“); bei Konflikt geht die Aufgabe an den Nutzer. Die Aufgabe wird nur angenommen, wenn Ticket, Nutzer und Aufgabe zusammenpassen (Mandantentrennung, Fall in `test_isolation.py`).
- Der Pi-Runner und der Mac-Runner haben dieselbe Schnittstelle. Jede Aufgabe trägt „braucht: Mac“ oder „egal“. Weitere Rechner lassen sich später ergänzen.
- Verworfen: Fernsteuerung der Claude-Desktop-App (kein verlässlicher, dokumentierter Weg bekannt) und offene Ports am Mac.

### Git in Kurzform

- Git ist die Versionsverwaltung. Es läuft lokal, speichert jede Änderung als Commit und erlaubt Branches und Zurückrollen. Kein Internet und kein Konto nötig.
- GitHub ist eine optionale Website, die Git-Repositories hostet. Pro Repository wählst du privat (nur du) oder öffentlich (alle sehen es). Es ist eine Zusatzkopie, kein Muss.
- Dein Aufbau: Das Haupt-Repo je Projekt liegt auf dem Pi. Pi-Runner und Mac-Runner holen und liefern per Git. Optional ein Spiegel in einem privaten GitHub-Repo als externes Backup.
- Board, Rollen und Freigabe macht dein Tool, Git speichert nur den Code. GitHub hat eigene Boards, die wir nicht brauchen.
- Begriffe: Commit = gespeicherter Stand mit Beschreibung. Branch = Arbeitslinie für eine Aufgabe. `main` = Produktivversion. Merge = Branch übernehmen. Tag = benannte Version (z. B. v0.3) zum Zurückrollen.
- Beispiel einer Aufgabe: `git switch -c fix-login`, Änderungen, `git commit -m "Fix login"`, nach Freigabe `git switch main` und `git merge fix-login`. Zurückrollen: `git revert <Commit>`.

### Bausteine aus Open Source (Recherche)

- Vibe Kanban (Apache-2.0): Kanban-Board, das Coding-Agenten wie Claude Code startet. Jede Aufgabe läuft in einem eigenen Git-Worktree, der Workflow-Status liegt in SQLite, der Code in Git. Es ist ein gutes Vorbild für unsere Architektur. Es startet Agenten standardmäßig ohne Rückfragen, ein Rollenkreislauf mit Tester, Prüfer und deiner Freigabe ist nach der Beschreibung nicht erkennbar.

- Vorschlag: Board und Rollenablauf selbst bauen, weil sie klein und sehr speziell sind. Muster von Vibe Kanban übernehmen (Worktree je Aufgabe, eine einheitliche Schnittstelle je Agent, Workflow in SQLite). Für Login, Passwort-Reset und Mailversand fertige Python-Bibliotheken nutzen.

### Benutzerverwaltung (nur Admin)

- Vier Rollen nach Rang (Nutzer < Admin < Superadmin < Owner; `users.RANK`): Owner (immer genau einer, zunächst Janis), Superadmin, Admin, Nutzer. Der Owner hat alle Admin-Rechte. **Superadmin (gebaut 16.11.2026, `superadmin`):** darf alles, was der Owner darf (Seite System, Neustart, Ausschalten, Backup, Servereinstellungen, später der Update-Knopf), mit zwei Ausnahmen: Er kann **keine Superadmins** und **den Owner nicht** bearbeiten, löschen, zurücksetzen oder herabstufen. Admins und Nutzer verwaltet er (auch Admin-Rechte vergeben und entziehen). Nur der Owner ernennt und entzieht Superadmins (Schalter „Superadmin“ in der Benutzerliste, ein entzogener Superadmin wird Admin) und übergibt die Owner-Rechte. Verwaltet wird nur ein Konto mit niedrigerem Rang (`can_manage`); Neustart und Ausschalten verlangen weiter das Passwort des Handelnden. Keine Schemaänderung (`users.role` ist freier Text), also keine Migration. Der Owner ist keine feste Person: Er kann die Owner-Rechte an ein anderes Konto übergeben (siehe unten).
- Keine Selbstregistrierung: Neue Konten legen nur Owner und Admins an.
- In den Einstellungen: „Benutzer hinzufügen“ nimmt nur die E-Mail-Adresse und schickt eine Einladungs-Mail (siehe unten).
- Liste der Benutzer: Passwörter zurücksetzen und Konten löschen (Owner und Admins).
- **Einladungslink erneut senden (Janis, 15.11.2026, `resend-invite`):** Bei Konten, die noch das Startpasswort haben (`must_change`), steht neben dem Schlüssel ein Kettenglied-Knopf („Einladungslink erneut senden“). Er schickt dieselbe Einladungsmail („Schön, dass du dabei bist“) mit einem neuen Link (7 Tage); der alte Link wird ungültig. Ohne Dialog, die Antwort steht in der Zeile unter der Rolle, kein Neuladen. Höchstens eine Mail je Konto und Minute (Sperre von `resets.create_token`); nur wer das Konto verwalten darf (Rangregel); bei Konten mit eigenem Passwort „schon gewählt“ (dafür gibt es „Passwort vergessen“). Scheitert die Mail, bleibt das Konto bestehen. Auch bei einem von Admins zurückgesetzten Passwort erscheint der Knopf, denn auch dort fehlt das eigene Passwort.
- **Konto löschen mit 30 Tagen Frist (Janis, 15.11.2026, `account-trash`):** Ein gelöschtes Konto wird zuerst nur **gesperrt** (`users.deleted_at`): kein Login, in keiner Liste, Sitzungen und Reset-Links enden, **Claude-Token und API-Schlüssel werden sofort gelöscht**. Projekte, Dateien, Chats und Einstellungen bleiben unberührt. Lädt ein Owner oder Admin **dieselbe Adresse** innerhalb von 30 Tagen (`users.DELETED_DAYS`) wieder ein, kommt genau dieses Konto zurück, mit allem wie vorher, aber immer **als Nutzer** (Adminrechte vergibt der Owner neu) und mit neuem Passwort über die Einladungsmail; nur die KI muss neu verknüpft werden. Nach 30 Tagen löscht `users.purge_deleted` alles endgültig: Zeile, Projekte, Board, Chats, Archiv, Dateien und über den Runner die Code-Repos und Arbeitsordner. **Es bleibt kein Vermerk**, dass es das Konto gab (Janis: gar nichts). Ausgelöst wird das Bereinigen, wenn der Runner nachfragt (`/runner/cleanups`) und beim Öffnen der Verwaltung. Die nächtlichen Backups halten den Stand noch bis zu etwa fünf Wochen (7 Tage täglich, 4 Sonntage), danach ist auch dort nichts mehr.
- **Projekt gelöscht:** Der Hub stellt Code-Repo und Arbeitsordner des Projekts in die Liste `work_wipes`; der Runner löscht sie (`Workspace.remove_project`, `remove`) und meldet es (`/runner/cleanups/done`), erst dann vergisst der Hub sie. **Nummern werden nicht neu vergeben, solange Ordner auf das Löschen warten** (`db.fresh_id`): SQLite gibt die Nummer der zuletzt gelöschten Zeile sonst wieder aus, und ein neues Projekt oder Konto hätte das alte Repo oder den alten Token geerbt.
- Philosophie: Der Admin kennt die Passwörter der Nutzer nicht und muss sich keine ausdenken. Beim Anlegen gibt er nur die E-Mail-Adresse ein; der Hub schickt eine Einladungs-Mail mit einem Link, über den der Nutzer sein eigenes Passwort festlegt (gleicher Baustein wie der Reset per E-Mail, der Link gilt 7 Tage). Das Konto bekommt bis dahin ein Zufallspasswort, das niemand kennt.
- Klappt der Mailversand nicht, wird das neue Konto wieder entfernt und der Admin sieht eine Meldung. Ohne Resend-Einstellungen (Abschnitt 9) lassen sich also keine Nutzer einladen.
- Ein vom Admin vergebenes Startpasswort gibt es nur noch beim Zurücksetzen eines bestehenden Kontos (Schlüssel-Knopf in der Liste). Es gilt bis zur ersten Änderung: Beim ersten Login muss der Nutzer ein eigenes Passwort setzen.
- Owner und Superadmin können Admin-Rechte per Schalter in der Benutzerliste vergeben oder entziehen (nur bei Konten unter ihrem Rang). Das Owner-Konto kann niemand löschen oder herabstufen; die Rolle wechselt nur durch die Übergabe.
- **Owner übergeben** (Janis, 07.11.2026, Branch `owner-transfer`): In der Benutzerliste hat der Owner pro Konto einen Kronen-Knopf „Zum Owner machen“. Der Dialog „Owner-Rechte übergeben?“ erklärt, dass die Person Owner wird und er selbst Admin, und verlangt sein Passwort (Sperre pro IP wie beim Löschen). Beide Änderungen geschehen in einer Transaktion (`users.transfer_owner`): erst wird der alte Owner Admin, dann der neue Owner; es gibt nie keinen und nie zwei. Nur der Owner darf das, nicht an sich selbst, und nur an Konten, die schon ein eigenes Passwort gewählt haben (sonst könnte die Rolle bei jemandem landen, der sich nicht anmelden kann; für solche Konten fehlt der Knopf). Der neue Owner hat sofort alle Owner-Rechte, der alte nur noch Admin-Rechte; Sitzungen bleiben bestehen. Zurück geht es nur, wenn der neue Owner wieder übergibt. Abgesichert an drei Stellen: `create_user` und `transfer_owner` im Code, dazu ein eindeutiger Teilindex `users_one_owner` in der Datenbank (`UNIQUE (role) WHERE role = 'owner'`). Der Index legt keine Person fest, er verbietet nur einen zweiten Owner.
- **Gebaut am 07.11.2026** (Branch `user-management`): Rollen `owner`/`admin`/`user` in `users.role`, Seite `/users` (seit 11.11.2026 als Block der Seite `/admin`, erreichbar über den Knopf „Verwaltung“ in der Einstellungs-Schublade, nur für Owner und Admins), Dialoge zum Hinzufügen, Zurücksetzen und Löschen. Zurücksetzen und Löschen verlangen das Passwort dessen, der es tut (mit der Sperre pro IP). Wer sich mit einem Startpasswort anmeldet, erreicht nur `/password`, bis er ein eigenes gesetzt hat; dabei enden seine anderen Sitzungen. Der Owner kann Admins ernennen und entziehen und alle anderen verwalten, Admins verwalten nur normale Nutzer, niemand rührt den Owner an. Beim Löschen eines Kontos verschwinden auch seine Projekte.

Mit dem Link legt man ein Passwort nach den üblichen Regeln fest; danach enden alle Sitzungen und ein Startpasswort-Zwang entfällt.
- **Gebaut am 07.11.2026** (Branch `invite-mail`): Die Mails (Reset und Einladung) sind HTML-Mails im Design des Hubs (`mailtext.py`): Begrüßung „Hallo Name,“ (Name oder Teil vor dem `@`), Text, großer Knopf in der Akzentfarbe, darunter der Link als Text und ein Hinweis zur Gültigkeit; dazu immer eine reine Textfassung. Es gibt zwei Farbstile (hell und dunkel, Werte aus DESIGN.md Abschnitt 2); verschickt wird der Stil, den der Nutzer zuletzt gesehen hat. Dafür merkt sich der Server die Wahl pro Konto (`users.theme`, `light` oder `dark`, Standard `light`): Der Schalter speichert weiter im Browser (`localStorage`) und meldet die Wahl zusätzlich per `POST /theme`; außerdem meldet jede angemeldete Seite beim Laden ihren Stil, wenn er vom gespeicherten abweicht (so zählt auch die Geräteeinstellung, und das zuletzt benutzte Gerät gewinnt). Mailprogramme wie Gmail färben dunkle Mails im Dunkelmodus eventuell selbst um. **Ersetzt am 16.11.2026 (`mail-rebuild`, DESIGN.md 10c):** keine Kopie des Seitenstils mehr; hell ist die Grundlage, dunkel folgt dem Mailprogramm des Lesers.
- **Passwortseite** (`/password`, 07.11.2026): Wer sich gerade mit einem Startpasswort angemeldet hat, sieht nur „Neues Passwort“ und „wiederholen“ (kein aktuelles Passwort, er hat es eben eingegeben und es ist ohnehin nicht seins; das neue darf nicht gleich dem Startpasswort sein). Wer sein eigenes Passwort ändert, gibt wie bisher das aktuelle an. Beide Seiten haben „Abbrechen“: normal zurück zum Dashboard, bei Startpasswort Abmelden (jede andere Seite schickt ihn sonst hierher zurück). Der Reset-Link aus der Mail (`/reset/{token}`) fragt nie nach dem alten Passwort und hat ebenfalls „Abbrechen“ (zur Anmeldung). In der Benutzerverwaltung heißt der Rückweg „Zurück“.
- **Passwortregeln** (Janis, 07.11.2026): für selbst gewählte Passwörter mindestens 6 Zeichen mit Groß- und Kleinbuchstaben, einem Sonderzeichen und zwei Zahlen (`users.password_problem`). Ein vom Admin vergebenes Startpasswort braucht nur 6 Zeichen, denn der Nutzer ersetzt es sofort. `users.set_password(user_id, neues_passwort)` prüft nur die Länge, beendet alle Sitzungen (außer der als `keep_token` übergebenen) und macht offene Reset-Links ungültig; wer ein Passwort wählen lässt, prüft vorher `password_problem` (so tun `/password` und `/reset/{token}`).
- Das Owner-Konto entsteht bei der Installation (`docker compose exec -it web python -m app.create_admin` im Ordner der `compose.yml`: das erste Konto wird Owner, weitere werden Admins). Ein normales Konto lässt sich nur über die Website einladen; per SSH gäbe es nur den Aufruf von `users.create_user` mit `python -c`, einen fertigen Befehl gibt es dafür nicht.

### Ablauf

1. Programmierer nimmt einen Punkt, arbeitet im Branch.
2. Tester prüft. Bei Fehlern zurück zum Programmierer.
3. Prüfer kontrolliert die Richtlinien. Bei Einwänden zurück zum Programmierer, danach wieder Tester.
4. Maximal 3 Durchläufe und ein Zeitlimit pro Aufgabe, danach geht der Punkt an Janis.
5. Janis gibt frei, als weiteres Glied der Kette: per Klick auf vorgefertigte Aussagen plus Freitextfeld (z. B. bei Fehlerbeschreibungen), Berichte lassen sich vorausfüllen. Danach wird der Branch in die Produktivversion übernommen.
6. Der Manager aktualisiert Dokumentation und Projektstand (früher Dokumentator, entfallen am 07.11.2026).

### Dateiablage

- Pro Projekt: Bilder, Dokumente, Webfunde.
- Inhalte gelten für Agenten als Daten, nie als Anweisung (Schutz vor Prompt-Injection).
- **Ein Dateiordner pro Projekt (Janis, 08.11.2026):** Alle Dateien, die zum Projekt gehören, liegen in **einem geschützten Ordner auf dem Pi**: Uploads (Bilder, PDFs, Datenblätter), Webfunde und **alle Markdown-Dateien** des Projekts, auch die des Managers (`MANAGER-MEMORY.md`, Projektstand, Doku-Entwürfe, Checklisten). Vorschlag für den Ort: `data/projects/<projekt-id>/files/`, Rechte 0700, nur Hub und die Läufe dieses Projekts; gehört dem Besitzer des Projekts (Mandantentrennung, Fall in `test_isolation.py`).

Lesen darf er alles; schreiben nur seine eigenen Dateien (Gedächtnis, Stand, Doku-Entwürfe, Checklisten), Uploads des Nutzers bleiben unangetastet (Vorschlag, passt zu „Vorschläge statt eigener Änderungen“). ## 6. Sicherheit und Datensicherung

- Keine offenen Ports, Zugriff nur über Tunnel.
- Passwörter nur gehasht, Zwei-Faktor-Anmeldung, Begrenzung falscher Anmeldeversuche.
- Sitzungen und Reset-Links stehen in der Datenbank nur als SHA-256-Hash, nie im Klartext: Eine Kopie der Datenbank oder ein Backup enthält keine nutzbare Anmeldung. Ein neues Passwort beendet alle anderen Sitzungen und macht offene Reset-Links ungültig. Reset-Mails sind pro IP begrenzt (wie falsche Passwörter, eigener Zähler) und pro Konto auf eine Mail je 60 Sekunden.
- Mandantentrennung: Jede Abfrage nach Projekten und Board-Punkten hängt an `user_id` (Punkte über ihr Projekt), ein fremder Zugriff liefert „nicht gefunden“ (404) oder „nichts getan“. `tests/test_isolation.py` und der HTTP-Test mit zwei Konten prüfen das. Neue Datenfunktionen übernehmen diese Regel von Anfang an (auch solche für Agenten).
- Zugangsdaten und Schlüssel nie im Code, nie im Git.
- Agenten laufen isoliert im Container und nur im Projektordner.
- Automatische Backups von Datenbank und Dateiablage auf ein zweites Medium, mit regelmäßigem Test der Wiederherstellung.
- Jede Version ist ein Git-Stand und lässt sich zurückrollen. Vor jedem Update ein Backup.
- Aktivitätsprotokoll: wer, welcher Agent, was geändert.

**Schnittstellen für später:** Jede Route hängt an einem eigenen Router (`routes/`), neue Bereiche (Agenten, Dateiablage, Tresor) kommen als weiteres Modul plus Router dazu, ohne `main.py` umzubauen. Die Anmeldeprüfung ist eine Abhängigkeit (`page_user` für Seiten, `api_user` für fetch-Aufrufe), eine Rollenprüfung lässt sich dort ergänzen. Neue Seiten bauen auf `ui.logged_in_page()` auf, neue Texte kommen in `i18n.py` in beide Sprachen, neue Symbole in `icons.py`. Claude-Vorschläge legt der spätere Agenten-Code mit `board.create_suggestion(user_id, project_id, kind, title)` an.

### Datenmodell (SQLite, `/data/hub.db`)

- `users`: id, email (eindeutig), password_hash (scrypt), role (`owner`/`admin`/`user`, höchstens ein `owner` durch den Teilindex `users_one_owner`), must_change_password, display_name, language (`de`/`en`), had_project, created_at.
- `sessions`: token_hash (SHA-256 des Cookie-Werts, nie der Wert selbst), user_id, expires_at (14 Tage). Cookie `session`: HttpOnly, SameSite=Lax, Secure über `HUB_SECURE_COOKIE=1`.
- `projects`: id, user_id, name (höchstens 60), page, position. Sechs Kacheln pro Seite; eine volle Seite schiebt ihr letztes Projekt auf die nächste (`projects.move`). Seiten ohne Projekte gibt es nicht. Löschen ist endgültig und verlangt das Passwort.
- `board_items`: id, project_id, kind (`bug`/`minor`/`major`), title (höchstens 200), source (`user`/`claude`), status (`open`/`proposed`/`trash`), position. Von Hand angelegte Punkte sind `open` und stehen oben, Vorschläge von Claude sind `proposed` und stehen unten. Jeder Zugriff prüft, dass das Projekt dem Nutzer gehört.
- `login_attempts`: ip (Schlüssel), failures, window_start, locked_until. Zählt falsche Passwörter pro IP (hinter dem Tunnel aus `CF-Connecting-IP`). Zehn Fehlversuche innerhalb von 30 Minuten sperren die IP für eine Stunde, dann antworten Anmeldung und Projekt-Löschen mit 429 (auch bei richtigem Passwort). Ein richtiges Passwort setzt den Zähler nicht zurück, er läuft mit dem Zeitfenster ab. Gezählt wird nie pro E-Mail, damit niemand den Owner aussperren kann.
- `password_resets`: token_hash (Schlüssel, SHA-256 des Tokens, der Token selbst steht nur in der Mail), user_id, created_at, expires_at. Gültig 1 Stunde, wird beim Benutzen gelöscht. Eine neue Anfrage ersetzt die alte; für dasselbe Konto geht frühestens nach 60 Sekunden eine neue Mail raus. Löscht man den Nutzer, verschwinden seine Tokens (Cascade).
- `claude_connections`, `agent_settings`, `agent_tasks`, `agent_runs`: Claude-Verbindung, Einstellungen, Aufgaben und Läufe der Agenten (Felder in `KONZEPT-AGENTEN.md`, Abschnitt 4). Alle hängen über Cascade am Nutzer bzw. Projekt.
- `ai_connections` (seit 14.11.2026): user_id, provider, status (`connecting`/`connected`/`expired`/`wipe`), previous (Zustand vor einer Prüfung), updated_at; Schlüssel (user_id, provider), **ohne Fremdschlüssel** (gelöschte Konten bleiben als `wipe`, bis der Runner die Schlüsseldatei gelöscht hat). Der Schlüssel selbst steht nie in der Datenbank.
- `users.deleted_at` (seit 15.11.2026): Zeitpunkt des Löschens, leer = aktives Konto; alle Abfragen nach Konten (`check_login`, `get_by_id`, `get_user`, `list_users`, `resets.create_token`) sehen nur aktive. `work_wipes` (seit 15.11.2026): kind (`project`/`task`), ref (Nummer), created_at; Ordner gelöschter Projekte, die der Runner noch löschen muss, **ohne Fremdschlüssel**; die Zeile geht, wenn der Runner den Ordner gelöscht hat.
- Neue Spalten (14./15.11.2026): `chat_messages.provider` (welche KI antwortet), `chat_messages.tried` (KIs, die die Frage nicht beantworten konnten, Rückfall), `agent_runs.provider`, `agent_tasks.merged` (0 offen, 1 zusammengeführt, -1 Konflikt), `projects.memory_seeded` ist die **Version** des Erinnerungs-Grundgerüsts (2 seit ARCHIVE.md).
- Wichtige Schlüssel: `agent_settings` `ai.default` (Standard-KI), `model.<rolle>.<anbieter>` und `effort.<rolle>.<anbieter>` (alte `model.<rolle>` gelten weiter für ihre KI), `net.<rolle>`, `autonomy`; `server_settings` `ai_catalog.<anbieter>`, `ai_parallel` (KI-Läufe gleichzeitig, 0 = keine Grenze), `upload_parallel`, `upload_request_mb`.
- Schemaänderungen laufen über `NEW_COLUMNS` in `db.py` (Spalten werden beim ersten Datenbankzugriff nach dem Start ergänzt). Umwandlungen alter Daten (Rollen aus dem früheren `is_admin`, Seiten der Projekte, Sitzungs-Hashes) laufen **einmalig** und nur für alte Datenbanken, nie bei jedem Start; vor dem Deploy einer Migration wird sie an einer Kopie der echten Datenbank geprobt. Vor jeder Änderung an Daten ein Backup.

### Arbeitsablauf vom PC aus (so wurde bisher gearbeitet)

Auf dem Windows-PC ist kein Git installiert und das Repo liegt nur auf dem Pi und bei GitHub. Claude arbeitet deshalb so (Janis muss dafür nichts tun):

1. **Bearbeiten lokal:** Dateien aus dem Klon per `scp` in einen Arbeitsordner (Scratchpad der Sitzung) holen, dort mit den Editier-Werkzeugen ändern (UTF-8 ohne BOM, Zeilenenden `\n`).
2. **Auf den Pi:** geänderte Dateien per `scp` in den Klon `/opt/agent-hub/workspaces/agent-hub` legen, vorher `git switch -c <thema>` dort (ein Branch je Thema).
3. **Testen im Container**, ohne den laufenden Dienst anzufassen (Abschnitt „Tests“), neuer Code über zusätzliches `-v "$PWD/web/app:/app/app"`.
4. **Committen** (ein Thema pro Commit, kurze englische Nachricht), `git switch main`, `git merge --no-ff <thema>`, `git push origin main`.
5. **Sichern und ausrollen:** Datenbank nach `/opt/agent-hub/backups/hub-<datum>-before-<thema>.db` kopieren, `docker compose up -d --build web`, dann `/health` und `https://hub.janis-home.de/login` prüfen und bei Datenbankänderungen die Tabellen ansehen.
6. **Schritte als Skriptdatei:** längere Abläufe als `.sh`-Datei per `scp` hochladen und mit `bash` ausführen (keine verschachtelten Anführungszeichen für `ssh` aus PowerShell). Skripte und Vorschau-Dateien liegen im Scratchpad, nicht im Projekt.
7. **Keine Ports für Vorschauen öffnen** (z. B. `http.server` auf dem Pi): Die Sicherheitsprüfung der Sitzung lehnt das ab. Mail-Vorschauen stattdessen als Datei erzeugen und im eingebauten Browser der Claude-App öffnen (dort nur ansehen, kein Bedienen).
8. **Zugangsdaten** (`.env`, Schlüssel) werden nie ausgegeben; Prüfungen zeigen nur Namen und Längen, nie Werte.

### Update-Ablauf

1. Backup der Datenbank: `cp data/hub.db /opt/agent-hub/backups/hub-$(date +%F).db` (im Klon-Ordner, Dienst darf laufen).
2. Änderungen auf einem Branch entwickeln und testen, dann nach `main` mergen und pushen.
3. Auf dem Pi im Klon-Ordner: `git pull`, dann `docker compose up -d --build web`. Ändert sich der Runner, die Schnittstelle zwischen Hub und Runner oder der Egress-Proxy: `docker compose build web runner && docker compose up -d web runner egress` (**Hub und Runner immer zusammen**, sonst gibt ein alter Runner z. B. Mistral-Fragen an Claude Code). Die Lauf-Images baut Compose nicht: bei Änderung von `runner/Dockerfile` `docker build -t agent-hub-agent -f runner/Dockerfile runner`, bei `runner/Dockerfile.vibe` oder `runner/vibe_entry.py` `docker build -t agent-hub-vibe -f runner/Dockerfile.vibe runner` (beide auch in `restore.sh`).
   Ordner auf dem Pi: `/opt/agent-hub/work` (Projekt-Repos `repos/`, Git der Aufgaben `gitdirs/`, Arbeitsordner `tasks/`; legt der Runner an, 0700; `repos/` ist im nächtlichen Backup).
4. Prüfen: `curl -s http://127.0.0.1:8000/health` und `https://hub.janis-home.de/login`.
5. Zurück: `git revert <Commit>`, erneut bauen; Daten notfalls aus dem Backup.

### Backup und Wiederherstellung (seit 11.11.2026)

**Was gesichert wird** (alles, was nicht aus GitHub neu entsteht): die Datenbank (`data/hub.db`, mit SQLites eigener Backup-Funktion konsistent kopiert), alles andere in `data/` (später Uploads), die `.env` des Hubs, `.env` und `compose.yml` des Tunnels, das Claude-Verzeichnis `/opt/agent-hub/claude` (die Logins aller Nutzer, nur root liest es), der GitHub-Schlüssel des Pi. Nicht gesichert: Code (GitHub), Docker-Images (werden gebaut), das Betriebssystem.

**Ablauf:** `deploy/backup.sh` läuft nachts um 03:15 Uhr als root per systemd-Timer (`agent-hub-backup.timer`, holt Verpasstes nach). Es packt alles in eine Datei `hub-JJJJ-MM-TT.tar.gz.gpg` auf dem Stick (`/mnt/backup/agent-hub/`), verschlüsselt mit AES-256 (`gpg`, Passwort in `/etc/agent-hub-backup.pass`, Modus 600), prüft danach, dass sich die Datei wieder öffnen lässt, und behält die letzten 7 Tage plus 4 Sonntage. Danach löscht es die Kopien vor Deploys in `/opt/agent-hub/backups/`, die älter als 35 Tage sind (`KEEP_COPY_DAYS`, seit 15.11.2026). **Achtung:** Der Timer startet die installierte Kopie `/usr/local/sbin/agent-hub-backup`, nicht die Datei im Repo; nach einer Änderung an `backup.sh` muss Janis sie neu installieren: `sudo install -m 700 /opt/agent-hub/workspaces/agent-hub/deploy/backup.sh /usr/local/sbin/agent-hub-backup`. Das Ergebnis steht in `backup.log` und `last-ok.txt` auf dem Stick. **Von Hand** gibt es den Knopf „Backup erstellen“ im Block System der Verwaltungsseite (Owner): Er startet dieselbe Systemd-Einheit `agent-hub-backup.service` wie der Timer, und zwar über den Runner wie bei Neustart und Ausschalten; der Runner wartet, bis das Backup durch ist, und meldet „ok“ oder „fehlgeschlagen“ zurück, die Seite zeigt es an. Ein Backup am selben Tag ersetzt das vom Timer. Einrichtung einmalig mit `sudo bash deploy/setup-backup.sh` (hängt den Stick per UUID ein, `nofail`, formatiert nichts, zeigt das Passwort nur einmal an). **Das Passwort gehört in den Passwortmanager und auf einen Zettel; ohne es sind die Backups wertlos.** Stick: FAT32 (von Windows und Mac direkt lesbar); die Dateien sind kleiner als 4 GB.

**Verworfen:** restic (eine Abhängigkeit mehr für wenige MB), ein Abbild der ganzen SD-Karte (läuft nicht sicher auf neuer Hardware wie einem Pi 5, 58 GB, der Hub müsste dafür stehen).

**Wiederherstellen** (`deploy/restore.sh`, Ablauf im Kopf der Datei): `restore.sh` einmal **vom PC auf den Stick kopieren** (das neue System kann es nicht von GitHub holen, der Schlüssel dafür steckt im Backup; Kopie im Projektordner unter `deploy/restore.sh`), neue SD-Karte mit Raspberry Pi OS Lite 64-Bit (Imager: Benutzer `admin`, Host, SSH-Schlüssel), Stick einhängen, `sudo bash /mnt/stick/restore.sh /mnt/stick/agent-hub` (nimmt das neueste Backup; fragt das Passwort). Das Skript öffnet und prüft das Backup **zuerst** (Passwort, Prüfsummen), ändert vorher nichts und schreibt nur in leere Orte, ein zweiter Lauf oder ein Pi mit Hub wird abgelehnt. Dann installiert es Git und Docker (offizielle Paketquelle), legt die Daten zurück, holt den Code mit dem Schlüssel aus dem Backup, setzt auf dem Pi den Speicherlimit-Eintrag (`cgroup_memory=1`, danach einmal neu starten), baut die Images (auch `agent-hub-agent`) und startet Hub und Tunnel. Cloudflare und Resend brauchen keine Änderung (Token und Schlüssel liegen in den `.env`; die Route steht bei Cloudflare). **Den alten Pi vorher ausschalten**, zwei Pis mit demselben Tunnel-Token teilen sich die Besucher. Danach: Claude-Verbindung ansehen (ein Login kann abgelaufen sein, dann neu verknüpfen) und `setup-backup.sh` erneut ausführen (neues Backup-Passwort, das alte für die alten Backups behalten).

**Geprüft** (11.11.2026): erster echter Lauf von `backup.sh` ohne Fehler; Datenteil von `restore.sh` mit einem Testbackup der echten Daten in einem Wegwerf-Ordner: alle Dateien identisch, Zeilenzahlen gleich, Datenbank intakt, Rechte stimmen; falsches Passwort und beschädigte Datei schreiben nichts. **Nicht geprüft:** Installation von Docker, `git clone`, Bauen und Starten auf einer wirklich neuen SD-Karte, die Wiederherstellung des Claude-Logins nach dem Umzug. Das geht nur mit einer echten Probe (Janis tauscht die Karte, der alte Pi bleibt aus). Auf einem anderen Gerät als einem Pi 4/5 (64-Bit ARM) sind die Images ungetestet.

**Entscheidungen und Konzept (17.11.2026, Janis):**
- **Anmeldung (entschieden):** Das Feld „Schlüssel“ wird zur Auswahl **„Anmeldung: Schlüssel oder Passwort“**; ein sudo-Passwort nur als bewusste Ausnahme, Normalfall ist die `sudoers`-Regel für die festen Befehle der Knöpfe; Tokens entfallen, solange kein Dienst mit Token angebunden wird.
- **Geheimnisse sind nicht auslesbar (Vorschlag, Janis neigt dazu: „sonst sind wir bei einem Passwortmanager, mit eigenen Tücken“):** Es gibt keine Funktion, die ein gespeichertes Geheimnis anzeigt, kopiert oder exportiert, nur Ersetzen und Entfernen. Technisch folgt das aus der asymmetrischen Verschlüsselung: nur der Vermittler kann entschlüsseln und gibt den Schlüssel nie weiter, kein Web-Weg liefert ihn. Folge: Ein verlorener Schlüssel wird ersetzt, nicht wiederhergestellt. Der private Schlüssel des Vermittlers (age) braucht eine eigene Sicherung, sonst sind alle gespeicherten Geheimnisse unlesbar und müssen neu eingegeben werden.
- **Schlüssel vom Hub erzeugen lassen (Vorschlag):** Neben „vorhandenen Schlüssel einfügen“ ein zweiter Weg „Schlüssel erzeugen“: der Vermittler erzeugt ein ed25519-Schlüsselpaar, sperrt den privaten Teil sofort ein und zeigt **nur den öffentlichen Teil** (eine Zeile) zum Kopieren auf das Gerät. Der Nutzer muss nie einen privaten Schlüssel anfassen; das ist der Weg, der ohne Kenntnis von SSH funktioniert.
- **Einrichtungsanleitungen (Konzept):** Keine festen Textblöcke (CLAUDE.md: Erklärungen als „i“), sondern ein **Dialog „Auf dem Gerät einrichten“**, den das Gerätefenster und das Ende von „Gerät anlegen“ öffnen. Er baut sich aus Bausteinen für **Betriebssystem-Profil × Schritt** auf und füllt Platzhalter aus dem Gerät (Hostname, Benutzer, öffentlicher Schlüssel), jeder Befehl in einem Block mit Kopieren-Knopf. Schritte: (1) **SSH einschalten** (Raspberry Pi OS: `raspi-config` oder Imager; Ubuntu und Debian: `apt install openssh-server`; Fedora: `systemctl enable --now sshd`; macOS: Einstellungen, Teilen, „Entfernte Anmeldung“; Windows: optionales Feature OpenSSH-Server, `Add-WindowsCapability`, Dienst starten; OpenWrt: Dropbear ist an); (2) **Benutzer anlegen** (eigener Benutzer, nie root); (3) **öffentlichen Schlüssel eintragen** (`ssh-copy-id` oder an `~/.ssh/authorized_keys` anhängen mit Rechten 700 und 600; Windows: bei Administratoren `administrators_authorized_keys` mit passenden Rechten); (4) **`sudoers`-Regel** (vom Hub aus dem Profil erzeugt, nur die Befehle der Knöpfe, mit `visudo -f /etc/sudoers.d/agent-hub`; Windows: Recht zum Herunterfahren); (5) **optional Passwort-Anmeldung abschalten**; (6) **„Verbindung testen“.** Dazu **Hilfe bei Fehlern**: jeder Fehlercode des Verbindungstests (nicht erreichbar, Port zu, Anmeldung abgelehnt, Hostschlüssel geändert, sudo nicht erlaubt) zeigt den passenden Schritt. **Wo läuft die Shell, und wie kommt ein Schlüssel sicher hinein (Janis, 17.11.2026):**
- **Die Shell läuft nie auf dem Server (Pi) selbst.** Der Vermittler öffnet eine SSH-Verbindung zum Gerät und fordert dort ein Terminal (PTY) an; der Browser zeigt nur diesen Datenstrom. Auf dem Server entsteht keine Shell, kein Benutzerkonto und kein Zugriff auf andere Benutzer oder Dateien des Servers. Will man von einem Gerät auf ein weiteres, startet man dort `ssh` mit den Schlüsseln, die auf diesem Gerät liegen; die Schlüssel des Hubs verlassen den Vermittler nie. Ein „Sprung“ über den Hub zu einem Gerät, das der Hub nicht kennt, gibt es nicht.
- **Schlüssel im Browser eingeben und unterwegs schützen:** Der Zugriff von außen läuft über den Cloudflare Tunnel, und Cloudflare beendet dort die TLS-Verschlüsselung; ein eingefügter privater Schlüssel (und ebenso jeder Terminal-Datenstrom) liegt auf diesem Weg technisch im Klartext bei Cloudflare, danach im Web-Dienst. Darum ist der Weg **„Schlüssel erzeugen“** der Standard: Es reist nur der öffentliche Teil. Wer einen vorhandenen privaten Schlüssel einfügt, sollte wissen, dass er diesen Weg nimmt; als spätere Verbesserung kann der Browser den Schlüssel **vor dem Absenden** mit dem öffentlichen age-Schlüssel des Vermittlers verschlüsseln (clientseitig, nur Geheimtext reist; braucht eine fest versionierte JavaScript-Bibliothek in `/static` und einen Eintrag in der Content-Security-Policy). Gleiche Grenze für Passwörter, die man in die Shell tippt.

**Standardweg der Shell (entschieden, Janis, 17.11.2026):** Browser → Web → Vermittler auf dem Pi → SSH zum Gerät im Heimnetz, auch von unterwegs („wie ein VPN“; Sonderfälle wie fremde Netze bekommen Sonderregeln später, Tailscale). Der SSH-Client läuft im Vermittler auf dem Pi, die Shell selbst auf dem Gerät. Anders als ein VPN öffnet das **kein Netz**: erreichbar sind nur die eingetragenen Geräte, nur per SSH und SFTP, nie andere Adressen des Heimnetzes.
- **Zwei Arten der Anmeldung in der Shell:** (a) **gespeicherte Zugangsdaten** (Schlüssel oder Passwort, verschlüsselt, der Vermittler meldet sich an, der Nutzer gibt beim Öffnen nur sein Hub-Passwort ein); (b) **im Terminal selbst eingeben** (Passwortabfrage von `ssh`, nichts wird gespeichert). Beide gehen über das Web (siehe oben, Cloudflare). **Kein Root:** auf vielen Systemen ist die SSH-Anmeldung als root ab Werk aus; empfohlen ist ein eigener Benutzer und in der Shell `sudo -i`, wenn man Administratorrechte braucht. Zugangsdaten von root im Hub zu speichern hieße, dass jeder Einbruch in den Hub volle Macht über das Gerät gibt; darum nicht als Standard, der Einrichtungsassistent führt zum eigenen Benutzer.
- **Dezenter Hinweis (Janis, 17.11.2026, „nichts Auffälliges, nichts Penetrantes“):** Neben der Überschrift der Shell ein „i“ (`ui.info_dot`) und beim Verbinden eine einzelne gedämpfte Zeile im Terminalfeld: „Diese Verbindung läuft über das Web. Gib nur ein, was du auch über das Web schicken würdest.“ (beide Sprachen in `i18n.py`). Kein Dialog, keine Bestätigung, keine Farbe außer gedämpft.

**Schlüssel gehört der KI, Passwort dem Menschen (Grundsatz, keine feste Regel; Janis, 17.11.2026):** Der **SSH-Schlüssel** wird gespeichert, damit KI-Instanzen (Claude und andere) über den Vermittler mit dem Gerät arbeiten können; die KI sieht den Schlüssel nie, sie löst nur feste, freigegebene Aktionen aus (nie die Shell, nie den Dateibrowser). Ein **Passwort** (Anmeldung oder sudo) ist **nur für den Menschen:** der Vermittler benutzt es ausschließlich für Sitzungen und Aktionen, die ein Mensch aus einer Browser-Sitzung heraus startet, nie für eine Anfrage aus einem KI-Lauf (Test: Anfrage mit Lauf-Ticket und Aktion auf einem Gerät, das nur ein Passwort hat, wird abgelehnt). Das ist der Normalfall (Musterbeispiel Raspberry Pi: Schlüssel für die KI, Passwort für den Menschen). **Umweg erlaubt (Janis):** Kann ein Gerät keinen Schlüssel haben (kein SSH-Schlüssel-Login möglich) und die KI soll damit nur mit Passwort arbeiten oder gar nicht, gibt der Mensch das **Passwort für die KI frei**: eigener Schalter am Gerät „Passwort darf auch von der KI genutzt werden“ (Standard aus, Hinweis per „i“: schwächer als ein Schlüssel). Die KI sieht auch dann nie das Passwort; der Vermittler setzt es nur für die festen Aktionen ein. Jede Nutzung steht im Protokoll mit dem Vermerk, dass sie von der KI kam. Ohne diesen Schalter bleibt ein Gerät nur mit Passwort für die KI unerreichbar (Test, plus Test, dass der Schalter die Anfrage zulässt). **Passwörter sind speicherbar** (entschieden, Janis): verschlüsselt, nur der Vermittler kann sie lesen. Neustart und Herunterfahren: Linux `systemctl reboot` und `poweroff` (ohne systemd `reboot` und `poweroff`), macOS `shutdown -r now` und `-h now`, Windows `shutdown /r /t 0` und `/s /t 0`. **Updates unterscheiden sich je Paketverwaltung:** Debian, Ubuntu, Raspberry Pi OS `apt-get update` und `apt list --upgradable`, dann `apt-get upgrade`; Fedora und RHEL `dnf check-update` (Rückgabewert 100 = Updates da) und `dnf upgrade`; Arch `checkupdates` (Paket `pacman-contrib`) und `pacman -Syu`; openSUSE `zypper list-updates` und `update`; Alpine `apk`, OpenWrt `opkg`; macOS `softwareupdate -l` und `-i -a`; **Windows hat keinen eingebauten Befehl** (Fremdmodul PSWindowsUpdate nötig, die schwächste Stelle). Mikrocontroller (ESP32, Arduino) und viele Router (Fritzbox) haben kein SSH: nur Online-Prüfung, keine Knöpfe. Ein Benutzer mit Rechten (Linux: `sudoers` nur für die Befehle; Windows: Recht zum Herunterfahren) muss einmal auf dem Gerät eingerichtet werden; dazu kommt eine kurze Anleitung je Betriebssystem. Online-Prüfung per TCP auf den SSH-Port, nicht per Ping (Windows blockiert ihn standardmäßig). **Reihenfolge der Unterstützung:** erst die Debian-Familie (Raspberry Pi OS, Ubuntu, Debian), dann andere Linux-Familien und macOS, danach Windows.

Der Effekt auf die Anzahl gleichzeitiger KI-Läufe ist ausdrücklich nicht gewünscht: Die Prozentregel regelt nur den Speicher, nicht die Zahl der Plätze (`serversettings.ai_parallel`).

**Upload: Stand der Untersuchung** (Janis hat eine 600er-Leitung, sie ist nicht die Bremse):
- Gemessen: Der Pi hängt per **WLAN** (`eth0` ist down), Signal gut; zum Internet 11 MB/s herunter und 7 MB/s hinauf; der Tunnel läuft über QUIC (UDP), Kernel-UDP-Puffer 4 MB (cloudflared wünscht etwa 7 MB); der Hub nimmt im Docker-Netz 12 bis 26 MB/s an. Echte Uploads kamen nur mit etwa 0,35 MB/s an.
- **Befund (13.11.2026, `upload-stream`):** Jede **einzelne Anfrage** kommt nur mit etwa **0,2 MB/s** durch den Tunnel, unabhängig von ihrer Größe. Deshalb lädt der Motor jetzt mit **sechs Anfragen gleichzeitig** hoch, der Server schreibt beim Eintreffen und behält bei einem Abbruch, was ankam (Einzelheiten im Änderungsprotokoll). Schneller als die Upload-Leitung des Anschlusses, von dem hochgeladen wird, wird es nie.
- **Gelöst (13.11.2026, abends): Der Tunnel läuft über HTTP/2 (TCP) statt QUIC (UDP).** Messung mit sechs Anfragen: über QUIC kamen **insgesamt** nur 0,3 MB/s an (jede Anfrage 0,05 MB/s, alle über eine Verbindung). Die Gegenprobe mit dem Speedtest von Cloudflare zeigte, dass beide Teilstrecken über TCP schnell sind: PC → Cloudflare 3,1 MB/s (während ein Upload lief), Cloudflare → Pi 11,3 MB/s. Also lag es an QUIC über WLAN. Nach der Umstellung (`--protocol http2` in `/home/admin/cloudflared/compose.yml`) kam eine 1,7-GB-Datei mit **3 bis 6,8 MB/s, im Mittel etwa 5 MB/s** an (jede Anfrage etwa 1 MB/s, 8 bis 10 MB groß), also etwa 17-mal schneller. **Das ist die Grenze des Anschlusses:** Bei freier Leitung schafft der PC zu Cloudflare 3,7 MB/s mit einer und 5,3 MB/s mit sechs Verbindungen; mehr Anfragen oder größere Stücke bringen daher nichts mehr (Janis fragte am 13.11.2026; ein Versuch mit 12 Anfragen bestätigte es). Wer einen anderen Tunnel oder Tarif hat, stellt Gleichzeitig und Größtes Stück auf der Verwaltungsseite ein (`upload-settings`). Ein Direktweg im Heimnetz ist bewusst nicht gebaut (Janis: eine einheitliche Lösung, große Uploads sind selten). Die 100 MB von Cloudflare Free gelten je einzelner Anfrage (Inhalt eines Requests), nicht für die Menge pro Zeit und nicht für die Zahl gleichzeitiger Anfragen. Arbeitsspeicher war nie der Engpass (558 MB frei, Hub etwa 50 MB, Tunnel etwa 30 MB). Die alte Fassung liegt als `compose.yml.before-http2` daneben; zurück: zurückkopieren, `docker compose up -d` im Ordner. Beide Protokolle sichern die Daten gleich (Bestätigung und Neusenden, Verschlüsselung mit Prüfsumme je Paket); dazu zählt der Hub nur ganze Blöcke, und `finish` verlangt alle. Eine Prüfsumme über die ganze Datei ist bewusst nicht gebaut (Janis: unnötig).
- **Weitere Maßnahmen, nur falls nötig und mit Janis’ Ja:** LAN-Kabel am Pi; `net.core.rmem_max` und `wmem_max` auf etwa 7,5 MB (`sudo sysctl`, nur sinnvoll, falls der Tunnel wieder auf QUIC soll). Möglich ohne Netzänderung, aber mit neuer Abhängigkeit: `uvicorn[standard]` (httptools) für schnelleres Einlesen.
